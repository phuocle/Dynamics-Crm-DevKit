RunAsync · Failure propagation và exit code của lệnh server

Một lỗi được ghi ra màn hình chưa chắc làm command thất bại. Cần chọn từng nhánh và chứng minh từ entry point.

BUG · B05 / F01 · PHẠM VI RỘNGCHƯA CHẠY TEST / CHƯA SỬA CODE
Snapshot: 6cc55c1d9f2913fed470c6f6f646356ab895cb2b · Source version 4.44.44.44 · Bắt đầu từ file 00 · Báo cáo gốc giữ nguyên

1. Phạm vi của một lượt làm việc

ServerCommand await RunAsync rồi kết thúc. DevKitCommand trả Success khi RunTaskAsync không throw. TaskServer có nhiều nhánh log + return/continue. IsOk hiện được gán từ việc kiểm tra solution tồn tại, không phải kết quả tổng hợp của deployment.

Trạng thái bằng chứng

Nếu validation bên ngoài thành công và lỗi bên trong chỉ được log, command có thể trả 0. Exception thoát ra vẫn được wrapper map đúng. Không được chữa bằng “if (!server.IsOk) throw” rồi coi đã xong: IsOk có thể true dù deploy thất bại.

Chủ sở hữu: CLI. Shared/helpers, tests và wrapper được đọc để hiểu ảnh hưởng; việc đọc không có nghĩa phải sửa chúng. Đây là hồ sơ chuẩn bị cho lượt AI tiếp theo, không phải bản sửa đã áp dụng.

2. Những hành vi phải giữ nguyên

  • Giữ tên server và alias plugin/workflow/dataprovider, arguments, JSON và exit-code constants hiện có.
  • Giữ hành vi thành công/no-op và --only-assembly.
  • Phân biệt command thất bại với rollback: exit nonzero không thu hồi thay đổi đã ghi.
  • Không đổi base command/ITask cho mọi task khi chưa chứng minh cần thiết.

Thay đổi hành vi chỉ chấp nhận trong case lỗi đã được xác định. Một điểm chưa hoàn chỉnh không tự động là lý do thay đổi contract đang dùng.

3. Cách phân tích và sửa nhỏ nhất

  1. Kiểm kê error exits từ RunAsync → DeployFilesAsync → DeployFileAsync → operation. Ghi rõ continue file/type hay return ở mỗi chỗ.
  2. Chọn một nhánh lỗi nhỏ trước; viết test command-level để thấy exit code sai, không chỉ kiểm tra đã ghi ActionError.
  3. So sánh cách dùng exception hiện có với trạng thái failure cục bộ của TaskServer. Ưu tiên cách ít tác động; chưa mặc định xây DeploymentResult mới cho toàn CLI.
  4. Tách quyết định “fail fast hay tiếp tục rồi báo failure”. Không âm thầm đổi thứ tự hoặc số artifact được xử lý trong patch sửa exit code.
Điều kiện hoàn thành

Có bằng chứng command-level cho nhánh được sửa, mapping code rõ ràng, không thay policy xử lý phần còn lại ngoài ý định. Không tuyên bố đã sửa mọi failure path nếu chỉ xử lý một nhánh.

Lệnh kiểm chứng gợi ý sau khi đã sửa code

Chạy tại repository root. Đọc workflow unit-test hiện hành trước khi thực thi; kiểm tra class/filter còn tồn tại. Nếu thêm test class mới, bổ sung vào filter. Lượt tạo tài liệu này không chạy các lệnh dưới.

dotnet test "DynamicsCrm.DevKit.Cli.UnitTests/DynamicsCrm.DevKit.Cli.UnitTests.csproj" --framework net10.0 --filter "FullyQualifiedName~TaskServerFakeSdkCoverageTests|FullyQualifiedName~TaskServerTests|FullyQualifiedName~TaskServerCoverageTests|FullyQualifiedName~DevKitCommandBaseCoverageTests|FullyQualifiedName~DevKitCommandDeepCoverageTests"

Không thu coverage/full release nếu không được yêu cầu. Test có state chung cần [DoNotParallelize]; giữ WaitScalePercent theo quy ước. Nếu thực sự sửa Shared hoặc command base, chọn thêm regression cho các consumer bị ảnh hưởng theo AGENTS.md.

5. Điểm dễ làm hỏng phần đang chạy

CI đang dựa vào exit 0 có thể bắt đầu báo failure đúng sau sửa; đây là thay đổi quan sát được và cần ghi trong mô tả patch. Các test “CompletesWithoutSdk” có thể đang đóng băng hành vi cũ; phải đọc assertion, không xóa test hàng loạt để lấy màu xanh.

Liên quan: 06.DeployCustomApiStepAsync.html · 12.UnregisterPluginTypeAsync.html · 01.CliLogSecureUnsecure.html

Một patch nên có một root cause. Hồ sơ liên quan giúp kiểm tra ảnh hưởng, không phải yêu cầu kéo tất cả vào cùng lần sửa. Quyền triển khai hoặc thay đổi scope đến từ yêu cầu mới của người dùng.
