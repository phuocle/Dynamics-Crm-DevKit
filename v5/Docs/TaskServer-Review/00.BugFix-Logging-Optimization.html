Nguyên tắc làm việc

Giữ nguyên những gì đang hoạt động. Lỗi nào chứng minh được thì sửa lỗi đó. Không sửa cả class lớn vì nó “chưa đẹp”, không đổi kiến trúc để chữa một lỗi cục bộ, không thay behavior hợp lệ chỉ để dễ viết test.

Bug

Có input, expected/actual và đường dữ liệu chứng minh. Viết regression rồi chọn patch nhỏ.

Nghi vấn

Cần tái hiện hoặc xác minh contract. Chưa đủ bằng chứng thì chưa coi là lệnh sửa.

Tối ưu

Có bottleneck và số đo trước/sau. “Ít code hơn” không phải bằng chứng nhanh hơn.

Component chính: CLI .NET 10; Shared chỉ được đọc theo dependency. Tại thời điểm tạo hồ sơ, chưa sửa source, chưa chạy build/tests, chưa kết nối Dataverse. Mọi mục dưới đây đều là trạng thái review tĩnh, không phải checklist đã hoàn thành.

3. Cách thực hiện để hạn chế vỡ dây chuyền

  1. Đọc HEAD hiện tại. Xem git status, AGENTS.md, caller/callee và test liên quan. Snapshot này chỉ là điểm xuất phát.
  2. Chọn một root cause. Ví dụ che secure value không kéo theo thay logger toàn CLI; gán image Id không kéo theo xóa image cũ.
  3. Chứng minh lỗi. Dùng input tối thiểu, request trace và assertion quan sát được. Test double không được tự bù Id hoặc nuốt exception.
  4. Nêu phạm vi ảnh hưởng. CLI/local function khác Shared helper, base command, MCP hoặc VSIX. Nếu phải mở rộng phạm vi, giải thích lý do cụ thể trước khi làm theo yêu cầu của lượt đó.
  5. Sửa ít nhất cần thiết. Giữ public command, JSON keys, attribute, GUID và hành vi no-op/state hợp lệ; không gộp formatting/refactor không liên quan.
  6. Kiểm chứng tương xứng. Build CLI và focused net10.0 tests; thêm regression của consumer khi thực sự sửa dùng chung. Không full release chỉ vì tài liệu có nhiều mục.
  7. Báo cáo đúng. Lỗi nào đã sửa, test nào đã chạy, case nào chưa cover, yêu cầu live test nào còn lại. Git revert chỉ phục hồi source; không phục hồi dữ liệu đã xóa.
Điểm cần tránh từ báo cáo gốc

DeploymentResult, engine discover/validate/plan/apply/verify, manifest và safe-prune là ý tưởng kiến trúc trong khảo sát rộng. Chúng không phải điều kiện bắt buộc để sửa secure log, wildcard, image Id hoặc package Id. Với exit code cũng phải cân nhắc cơ chế hiện có trước khi thay ITask/base command.

4. Log và tối ưu: giới hạn rõ ràng

Log

Che nội dung secure config nhưng giữ thông tin hành động, tên type/step và trạng thái. Log “deployment stopped” phải phù hợp với flow thực tế; đổi message không tự sửa failure propagation. Chỉ dùng secret sentinel giả khi test. Đọc các đường exception nếu chúng có thể mang lại giá trị đã che ở happy path.

Tối ưu

Đo request counts, batch boundaries, paging và local overhead trước. Chưa có số đo production về latency trong bộ hồ sơ này. Không tự tăng song song, đổi tất cả List sang Dictionary hay cắt field truy vấn khi chưa biết consumer dùng gì. Nếu giữ nguyên là lựa chọn tốt nhất sau review, đó là kết quả hợp lệ.

Giới hạn không tự chuyển thành bug

Identity cũ không được tự upgrade; bỏ attribute không tự xóa registration; workflow package bị từ chối là giới hạn nền tảng. Các hành vi này cần được bảo toàn trừ khi người dùng chọn một nhiệm vụ khác có phạm vi rõ.
