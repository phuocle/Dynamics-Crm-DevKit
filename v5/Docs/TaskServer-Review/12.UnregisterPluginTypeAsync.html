UnregisterPluginTypeAsync · Bảo vệ binding khi unregister một type

Ưu tiên review thao tác ghi/xóa: unregister type A không được gỡ handler B của một Custom API chỉ vì message name trùng.

ĐƯỜNG GHI SAI CÓ ĐIỀU KIỆN · B06CHƯA CHẠY TEST / CHƯA SỬA CODE
Snapshot: 6cc55c1d9f2913fed470c6f6f646356ab895cb2b · Source version 4.44.44.44 · Bắt đầu từ file 00 · Báo cáo gốc giữ nguyên

1. Phạm vi của một lượt làm việc

Hàm tìm type theo full name, tra Custom API bằng attribute.Message, set plugintypeid=null khi tìm đúng một API, rồi xóa các step của type và xóa type. Nhánh gỡ API chưa so sánh binding hiện tại với type đang unregister. DeployCustomApiStepAsync có kiểm tra tương ứng ở nhánh Deactivate.

Trạng thái bằng chứng

Phát hiện bổ sung khi chia tài liệu: với API đang trỏ type B và attribute.Unregister của type A có cùng Message, code gửi update gỡ binding của B. Cần fixture đi qua caller để xác nhận điều kiện thật. Đây là lỗi tiềm năng của thao tác hiện có, không yêu cầu thêm tính năng unregister/prune mới.

Chủ sở hữu: CLI. Shared/helpers, tests và wrapper được đọc để hiểu ảnh hưởng; việc đọc không có nghĩa phải sửa chúng. Đây là hồ sơ chuẩn bị cho lượt AI tiếp theo, không phải bản sửa đã áp dụng.

2. Những hành vi phải giữ nguyên

  • Unregister vẫn là opt-in từ attribute; bỏ một attribute khỏi source không tự cho phép xóa.
  • Chỉ thao tác lên type/step/binding thuộc đối tượng đã xác định.
  • Giữ lỗi dependency do Dataverse trả; không tự xóa workflow/API/provider phụ thuộc để vượt lỗi.
  • Không thêm general cleanup, cascade thủ công, rollback hoặc xóa secure config “mồ côi” trong cùng patch.

Thay đổi hành vi chỉ chấp nhận trong case lỗi đã được xác định. Một điểm chưa hoàn chỉnh không tự động là lý do thay đổi contract đang dùng.

3. Cách phân tích và sửa nhỏ nhất

  1. Seed type A, type B và API→B; gọi unregister A với Message của API. Capture update/delete trước fake xử lý.
  2. Chọn guard ownership nhỏ nhất cho lookup API trước khi gỡ. Cân nhắc cache có thể stale trong cùng run; kiểm tra trace nếu trước đó binding đã đổi.
  3. Thử API→A, API không binding, missing type, lỗi delete step/type. Phối hợp file 05 để báo failure chính xác.
Điều kiện hoàn thành

Regression bảo vệ API→B, unregister hợp lệ API→A vẫn đúng, không xóa thêm loại tài nguyên nào. Mọi thử nghiệm live nếu cần phải là yêu cầu riêng với dữ liệu test xác định.

Chạy tại repository root. Đọc workflow unit-test hiện hành trước khi thực thi; kiểm tra class/filter còn tồn tại. Nếu thêm test class mới, bổ sung vào filter. Lượt tạo tài liệu này không chạy các lệnh dưới.

Không thu coverage/full release nếu không được yêu cầu. Test có state chung cần [DoNotParallelize]; giữ WaitScalePercent theo quy ước. Nếu thực sự sửa Shared hoặc command base, chọn thêm regression cho các consumer bị ảnh hưởng theo AGENTS.md.

5. Điểm dễ làm hỏng phần đang chạy

Đây là đường destructive nên fixture và điều kiện ownership quan trọng hơn việc giảm số dòng code. Không chạy unregister trên tenant thật trong lúc tái hiện unit test. Revert code sau một lần xóa không phục hồi record: đừng gọi git revert là rollback dữ liệu.

Liên quan: 05.RunAsync.html · 06.DeployCustomApiStepAsync.html · 11.DeployPluginTypeAsync.html

Một patch nên có một root cause. Hồ sơ liên quan giúp kiểm tra ảnh hưởng, không phải yêu cầu kéo tất cả vào cùng lần sửa. Quyền triển khai hoặc thay đổi scope đến từ yêu cầu mới của người dùng.
