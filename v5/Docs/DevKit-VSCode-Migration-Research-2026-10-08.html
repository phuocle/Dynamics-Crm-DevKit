01 / KẾT LUẬN

Nên chuyển trải nghiệm sang VS Code, theo từng nhóm khả năng.

Đề xuất: TypeScript extension + UI native/Webview + backend C# qua CLI. Tận dụng các command, Dataverse service, code generator và analyzer hiện có; viết adapter thay cho EnvDTE, wizard Visual Studio và WPF. Tiếp tục duy trì VSIX trong thời gian VS Code đạt độ ổn định.

Dialog: Quick Pick/InputBox cho thao tác ngắn; Webview Panel cho form có nhiều trường phụ thuộc nhau; Custom Text Editor cho chỉnh sửa RDL/dataset gắn với tài liệu.

Templates: dùng dotnet new cho khung project/file tĩnh, kết hợp dịch vụ sinh mã C# cho nội dung phụ thuộc metadata. Giữ một catalog logic chung và một luồng xem trước → kiểm tra xung đột → tạo file. T4 cần một host không phụ thuộc Visual Studio.

Mốc thành công đầu tiên: trên cả ba OS, người dùng kết nối Dataverse, tạo WebResource TS hoặc ConsoleCore project, thêm item theo entity/form, xem trước và triển khai một web resource lên môi trường thử nghiệm. Server/plugin là nhánh kế tiếp sau khi giải quyết build và đọc assembly.

Ba điều cần phân biệt ngay từ đầu

VSIX hiện tại không chỉ khai báo VS 2026

Manifest cho phép [17.0,19.0), tức dải major 17 và 18. Vì vậy nhận định “chỉ VS 2026” quá hẹp nếu xét điều kiện cài đặt. Đây là khả năng được khai báo, chưa phải xác nhận đã test mọi bản VS trong dải. Dependency Windows vẫn rõ ràng. [R01] [M23]

Cùng đuôi .vsix không cùng runtime

VS Code cũng đóng gói extension thành .vsix, nhưng dùng manifest và extension API riêng. Đổi package, cài VSIX cũ hoặc đổi target framework không chuyển được WPF/EnvDTE thành UI VS Code. Đây là công việc xây frontend và adapter mới. [M16] [R01]

Extension đa nền tảng ≠ mọi project chạy cục bộ

Editor có thể hoạt động trên Mac/Linux, trong khi assembly Dataverse vẫn target .NET Framework. Biên dịch, thực thi test, profiler/debug và report designer là bốn khả năng khác nhau, cần công bố riêng.

VS Code desktop ≠ vscode.dev độc lập

Backend .NET cần tạo process. Web extension trong browser không có khả năng này; Codespaces có remote extension host là một tình huống khác. Ưu tiên desktop trước, sau đó SSH/WSL/Dev Containers. [M08] [M09]

Phạm vi tài liệu: nghiên cứu VSIX chính, CLI, Shared và payload project/item templates. Không chạy build, không cài extension, không gọi Dataverse, không sửa cấu hình, không thay đổi version/timestamp. Các mốc thời gian và thiết kế sau đây là đề xuất kỹ thuật, không phải tính năng đã có.

Chia sẻ C# giữa net48 và net10.0

Giữ cách import Shared source hiện có trong giai đoạn đầu. Nếu sau này đóng gói library chung, phải kiểm tra API/dependency rồi chọn target tương thích hoặc multi-target; VSIX net48 không thể dùng trực tiếp library chỉ target net10.0. Tách DTO và pure logic trước, cô lập các host-specific adapter. Không đưa WPF/EnvDTE vào backend mới.

Không phụ thuộc vào command nội bộ hoặc DOM của Microsoft C# Dev Kit/Power Platform Tools. DevKit nên có catalog và menu riêng, gọi public VS Code API và CLI được tài liệu hóa. Power Platform Tools đã có extension trên ba OS, là bằng chứng tốt cho mô hình này; chưa phải bằng chứng rằng toàn bộ tính năng DevKit đã được Microsoft extension thay thế. [M15]

Luồng đề xuất: chọn target folder trong Explorer → New DevKit Item → chọn Plugin → điền form → xem diff/file mới → Create → mở file. Deploy là một action có chủ đích tiếp theo. Người dùng có thể tạo mã mà không vô tình đăng ký plugin lên môi trường.

Các yêu cầu UX để không giảm chất lượng so với VSIX

  • Metadata lookup bất đồng bộ, cache theo environment và truy vấn; có nút refresh. Request cũ trả về sau khi người dùng đổi entity không được ghi đè kết quả mới.
  • Back giữ lựa chọn còn hợp lệ; cancel không để file dở dang; reload panel phục hồi bản nháp không chứa secret. Validation quyết định cuối vẫn ở backend.
  • Keyboard navigation, focus, screen reader, high contrast, theme variables, zoom 200%; form vẫn dùng được trong editor hẹp.
  • RDL nên dùng TextDocument làm nguồn dữ liệu và apply edit có kiểm tra version. Không ghi XML trực tiếp ra đĩa khi tài liệu đang dirty; giữ phần layout/expression không thuộc dataset.
  • Webview chỉ gửi message theo allowlist/schema đến extension; extension mới gọi backend. Áp dụng CSP, resource URI của VS Code, escape dữ liệu metadata và không nạp script CDN.

Webview message passing/theming/security: VS Code Webview API. Native UX và accessibility: Webview UX guidelines. Các hành vi cụ thể ở trên là đề xuất áp dụng cho DevKit.

Không chọn @vscode/webview-ui-toolkit cho frontend mới. Blog Microsoft năm 2021 giới thiệu toolkit, nhưng repository Microsoft thông báo deprecate từ 01/01/2025. Đề xuất HTML semantic + CSS theme tokens; có thể dùng React cho state/form phức tạp nếu team quen. Chọn thư viện UI còn được duy trì sau một spike accessibility, không mặc định theo sample/blog cũ. 05 / PROJECT & ITEM TEMPLATES

Hai lớp sinh nội dung, một trải nghiệm thống nhất

Lớp 1: scaffolding tĩnh bằng .NET Template Engine. Chuyển nội dung template phù hợp sang .template.config/template.json, có identity/shortName, parameters, symbols, điều kiện file và cấu hình rename. Thay IWizard bằng pipeline có thể test độc lập

  1. Discover: đọc catalog đi kèm bản extension/template package; lọc theo loại folder/project, prerequisites và khả năng trên OS hiện tại.
  2. Collect: UI chọn project name, namespace, environment và metadata. Tạo một request trung lập với IDE.
  3. Validate: kiểm tra tên, target path, target framework, metadata, quyền ghi và dependency. Kết quả nêu lỗi tại từng trường.
  4. Plan: sinh vào vùng staging, trả về danh sách create/update/conflict, content preview và điều chỉnh project/solution dự kiến.
  5. Apply: chỉ ghi các file được chấp nhận; kiểm tra lại file đã đổi kể từ preview. Không dùng --force để bỏ qua xung đột. Ghi theo giao dịch ứng dụng: có backup/rollback và danh sách thao tác; không giả định nhiều file có thể atomic như một file.
  6. Finalize: cập nhật solution hoặc workspace cần thiết, mở file, hiển thị tác vụ tiếp theo. Restore/build là bước nhìn thấy được, có trạng thái lỗi riêng.

Pipeline và catalog là thiết kế mới đề xuất. Không có lệnh devkit scaffold được xác nhận trong CLI hiện tại; tên lệnh mới, nếu cần, phải chốt trong thiết kế sau. Giữ nguyên command/tool/JSON key hiện có.

  • Ưu tiên giữ nguyên T4Context và ngữ nghĩa template. So output của các default template và bộ custom template thực tế với baseline VSIX, chỉ chuẩn hóa các phần cố ý không ổn định.
  • Kiểm tra include path, assembly references, host-specific directive, encoding, newline, line directives và lỗi compile; mẫu nào gọi DTE/VS service phải chuyển hoặc ghi rõ chưa hỗ trợ.
  • Export/import custom templates giữ Title/Type/IsDefault/content theo schema cũ đã xác minh; không tự reset template của người dùng khi cập nhật.
  • T4 chạy C# nên được xem như code có khả năng thực thi. Chỉ chạy template trong workspace được trust; process riêng giúp quản lý lỗi/cancel nhưng không phải security sandbox.
Một nuance về Visual Studio: tài liệu .NET hiện nêu project/solution template có thể xuất hiện trong Create a new project, nhưng item template của dotnet new không tự xuất hiện trong Add → New Item. Vì vậy nếu tiếp tục duy trì VSIX, vẫn cần adapter/menu cho item và UI metadata; “một template engine” không có nghĩa “không còn integration code”. [M07]

08 / TÍCH HỢP BACKEND

CLI trước, tăng protocol khi có nhu cầu thật

PoC: gọi command CLI hiện có cho tác vụ dài và dùng devkit tool call … --output json cho tool có schema/result phù hợp. Repository đã có pipeline structured output và exit code riêng. Chỉ dùng tên/tool/options sau khi đối chiếu tool list/tool describe của phiên bản cài đặt; tool surface không tự bao phủ mọi wizard. [R13]

Beta: nếu cần giữ connection/metadata cache và gọi nhiều lần liên tiếp, cân nhắc process sống theo workspace với protocol request/response có version. MCP stdio là một lựa chọn tái dùng khi tool contract khớp; JSON-RPC riêng cũng có thể thích hợp cho scaffolding. Chốt bằng đo latency, cancellation và mức thiếu API ở PoC, tránh xây hai protocol cho cùng một chức năng.

Hợp đồng đề xuất

Request ID, protocol version, capability negotiation, validation errors, diagnostics, progress, cancellation, timeout và results tách khỏi log. Ngăn stdout log làm hỏng JSON/stdio protocol. Không đổi JSON keys/tool names hiện có; hợp đồng mới được version riêng.

Vòng đời process

Backend chạy cạnh workspace; khởi động theo nhu cầu, kiểm tra version và đóng khi dispose. Tách phiên theo environment; không để static metadata cache dùng nhầm tenant. Job bị hủy phải dừng process con và báo trạng thái sau cùng.

Authentication phải có một nơi chịu trách nhiệm

Đề xuất backend C# quản lý token acquisition/refresh/cache; VS Code lưu preference/profile reference, hoặc secret cấu hình cần thiết trong SecretStorage. Không truyền password/token vào Webview, output log hay command line hiển thị. Nếu backend mới cần nhận credential từ extension, thiết kế IPC kín có schema thay vì thêm secret vào argv.

MSAL có serializer đa nền tảng qua Microsoft.Identity.Client.Extensions.Msal; thay adapter DPAPI bằng cơ chế được hỗ trợ theo OS là hướng cần thử. SecretStorage bảo vệ dữ liệu của extension, không tự giải quyết token cache của CLI và không tự đồng bộ giữa các máy. Linux headless/container cần hành vi rõ khi không có secure store: phiên in-memory hoặc cấu hình được duyệt, không âm thầm hạ xuống plaintext. [M19] [M20]

Giữ quy tắc connection hiện tại: CLI thông thường/devkit tool call dùng explicit arguments rồi fallback project .env; devkit mcp chỉ nhận explicit connection, không tự đọc .env hoặc biến môi trường. FromPac hiện đọc các file/cache của PAC, cần test phiên bản và nền tảng; không coi đây là public token-sharing API ổn định. Auth AD/on-prem được xếp compatibility track riêng. [R09] [R14]

Remote, workspace và phát hành

  • Định hướng extensionKind: ["workspace"] vì extension thao tác file và chạy backend; Webview vẫn hiển thị ở client. Backend chạy trong WSL/SSH/container nơi workspace ở, không chọn binary theo OS của màn hình người dùng. [M08]
  • Dùng URI/workspace API cho tác vụ editor; chỉ chuyển sang đường dẫn OS ở ranh giới process của workspace host. Multi-root phải chọn đúng folder và project, không lấy workspace đầu tiên một cách ngầm định.
  • PoC dùng .NET SDK 10 + CLI/template version được pin. Phân biệt runtime để chạy CLI và SDK để dotnet new/build. Product có thể dùng backend riêng trong vùng lưu trữ extension hoặc package theo OS/architecture; không tự update global devkit và phá môi trường CLI của người dùng.
  • Nếu bundling self-contained backend, cần artifact theo Windows/macOS/Linux và kiến trúc tương ứng; metadata package vsce --target hỗ trợ cách phân phối này. Self-contained backend không thay SDK cần cho build project. [M16]
  • Task Provider + ProcessExecution cho job CLI được kiểm soát, problem matcher đưa lỗi về Problems. ShellExecution chỉ dùng khi thực sự cần shell và có escaping theo OS. Không nối input người dùng thành chuỗi shell. [M21]
  • Workspace chưa trust chỉ cho xem dữ liệu/template an toàn; chặn build scripts/T4/restore thực thi code cho tới khi đủ trust. Sinh file không tự deploy. [M24]

Analyzers: package hiện target netstandard2.0 nên có khả năng tiếp tục dùng qua NuGet. Vẫn phải kiểm chứng diagnostics/code fixes trong compiler và C# language service đã chọn; dependency Roslyn của analyzer có thể mới hơn host của người dùng. Không dùng target framework của analyzer làm bằng chứng đầy đủ về IDE compatibility. [R15]

Năm spike cần làm khi bắt đầu triển khai

  1. Auth & cache: Interactive/DeviceCode → đọc identity/metadata → đóng process → mở lại → silent refresh/logout trên cả ba OS, kể cả Linux không có desktop keyring.
  2. WebResource vertical slice: tạo TS project → sinh form cho một entity → npm build → upload JS build output. Kiểm tra đường dẫn có dấu/cách và folder phân biệt chữ hoa/thường.
  3. Plugin: generate net462 Server/Package mẫu → dotnet build → inspect registration → deploy lên sandbox. Chạy test/debug được đánh giá riêng.
  4. T4: chạy default Plugin, Workflow, CustomApi, DataProvider, Test và ít nhất một custom template thực tế; so tên file/nội dung/encoding/context với VSIX.
  5. UX: thử FormPlugin Webview và RDL dataset editing với keyboard, light/dark/high contrast, undo/save/reload. Mời người dùng VSIX hiện tại đánh giá số thao tác và tính dễ hiểu.
Quy tắc dừng có kiểm soát: nếu P0 plugin workflow chưa portable, vẫn có thể phát hành MVP JS/TS/ConsoleCore và ghi rõ giới hạn. Nếu auth hoặc generator cốt lõi thất bại trên một OS, không quảng bá hỗ trợ OS đó trước khi có đường đi đã xác minh.

Triển khai song song với VSIX như thế nào?

Mỗi workflow được chuyển có golden output/behavior test dùng chung. Frontend mới đọc cấu hình hiện có và chỉ thêm metadata tương thích khi đã có schema/version plan. Tách vòng phát hành extension với backend, nhưng có compatibility range và capability check. Giữ VSIX là lựa chọn cho workflow Windows chuyên biệt tới khi dữ liệu sử dụng và test đủ để quyết định thay thế.

Các quyết định trên là đề xuất, không phải yêu cầu phê duyệt để hoàn thành tài liệu này. Không có thay đổi mã sản phẩm hay scaffold project thực tế được thực hiện trong task nghiên cứu.
