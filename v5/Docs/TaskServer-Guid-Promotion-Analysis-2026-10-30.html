01. Trả lời ngắn

Tầng 1 — Deploy nhanh sang UAT/TEST (đã có)

TaskServer không cần solution được tạo/add component bằng tay. Mỗi lần chạy, CLI tự tìm record theo khoá tự nhiên (tên assembly, typename, tên step, tên image), create hoặc update, và gắn tham số SolutionUniqueName nên component được add thẳng vào solution trong DynamicsCrm.DevKit.Cli.json.

Điều kiện duy nhất: solution có cùng uniquename phải tồn tại sẵn ở môi trường đích (IsValidAsync chặn nếu thiếu). Tạo một solution rỗng ở UAT/TEST một lần là đủ, không cần add assembly/type/step thủ công nữa.

Tầng 2 — Cùng GUID ở mọi môi trường (mới có một phần)

Hiện chỉ step tái sử dụng GUID từ CrmPluginRegistration(Id = "..."). Assembly, plugin type, image, package, managed identity đều do server (hoặc Guid.NewGuid()) sinh mới ở từng môi trường → DEV ≠ UAT ≠ TEST.

Muốn đồng nhất cần: thêm thuộc tính chứa GUID cho assembly/type/image/package, cho CLI tìm theo GUID rồi mới tìm theo tên, create với GUID chỉ định, và ghi ngược GUID vào source sau lần deploy DEV.

Khuyến nghị: triển khai theo thứ tự (1) chuẩn hóa quy trình dùng TaskServer cho UAT/TEST ngay — không cần đổi code; (2) mở rộng "explicit GUID" cho type/image/assembly/package + báo cáo drift; (3) bổ sung lệnh ghi ngược GUID; (4) tuỳ chọn GUID tất định (UUID v5) cho component mới để giảm nhu cầu ghi ngược. Chi tiết ở §08.
Ngoại lệ quan trọng: với .nupkg (plugin package), Dataverse tự tạo pluginassembly/plugintype từ package; code hiện tại cũng không tạo type cho nuget (DeployPluginTypeAsync trả về record có sẵn). Vì vậy với package chỉ kiểm soát được GUID của package, step, image — không kiểm soát được GUID assembly/type (cần spike xác nhận, §13).

03. TaskServer hôm nay làm gì khi deploy

Luồng chính trong TaskServer.cs:

  1. IsValidAsync (dòng 578–602): kiểm tra profile, folder, và Deployment.IsExistSolutionAsync(Json.solution); lấy prefix publisher.
  2. DeployFilesAsync (106–196): với mỗi .dll/.nupkg → ký managed identity nếu có → deploy.
  3. DeployFileAsync (928–1045): nạp cache type/step/image/secure config/sdkmessage/custom API theo lô 50, rồi deploy assembly → type → step → image → custom API binding → data provider.
  4. Mọi Create/Update quan trọng đều gửi request.Parameters.Add("SolutionUniqueName", Json.solution) ⇒ component vào solution tự động.
  5. So sánh nội dung/thuộc tính trước khi Update ⇒ chạy lại nhiều lần là idempotent (log DO_NOTHING).
Hệ quả thực tế: chỉ cần trong UAT có solution trống PluginA (cùng publisher prefix), chạy devkit server với connection UAT là UAT có đủ assembly/type/step/image và chúng nằm trong solution PluginA. Bước tạo solution + add component thủ công có thể bỏ ngay mà không cần sửa code.
# Ví dụ — cùng profile, chỉ đổi connection
devkit server --profile DEV  --conn "AuthType=OAuth;Url=https://contoso-dev.crm.dynamics.com;..."
devkit server --profile DEV  --conn "AuthType=OAuth;Url=https://contoso-uat.crm.dynamics.com;..."
devkit server --profile DEV  --conn "AuthType=OAuth;Url=https://contoso-test.crm.dynamics.com;..."

Minh họa cú pháp; dùng --conn hoặc .env (DEVKIT_*) theo thứ tự ưu tiên auth của CLI. Không ghi secret vào file commit.

06. Phát hiện trong code liên quan trực tiếp

  1. Id đang mang hai nghĩa. VSIX CommandAddCrmPluginRegistration.cs: plugin ghi Id = stepId (dòng 392), workflow ghi Id = pluginTypeId (dòng 299). CLI chỉ hiểu Id là step ID; với workflow (không có step) giá trị này bị bỏ qua. Cần chốt ngữ nghĩa trước khi mở rộng.
  2. Không được đặt tên thuộc tính mới là TypeId. System.Attribute đã có property ảo TypeId; dùng PluginTypeId.
  3. Drift im lặng. Khi attribute có Id nhưng UAT đã có step cùng tên được tạo trước đó (GUID khác), lookup theo Id thất bại, fallback theo tên tìm thấy → CLI update record UAT và giữ GUID cũ. GUID lệch tồn tại mãi mà không có cảnh báo.
  4. Lookup theo Id không kiểm tra type sở hữu. Cache step được nạp theo các type của assembly; tìm bằng Id không xác nhận step đó thuộc pluginTypeId đang xử lý, và comparer IsChangedPluginStep không so plugintypeid (đã ghi nhận trong phân tích 29/09).
  5. Copy-paste class kèm Id rất nguy hiểm. Hai attribute trùng Id → bước thứ hai update đè step của bước thứ nhất. Chưa có preflight hay analyzer phát hiện trùng Id.
  6. VSIX "Update Crm Plugin Registration" chỉ chèn Id step khi khớp tên step (regex StepNameRegex); không ghi GUID image/type/assembly và phụ thuộc định dạng attribute dạng chuỗi.
  7. Managed identity tạo với Guid.NewGuid() phía client; app ID đầu tiên trong danh sách luôn được bind (biến isDevApplication). Đa môi trường cần ánh xạ app theo môi trường — không chỉ là chuyện GUID.
  8. Lỗi nhỏ: FetchXML dòng 848 có ký tự thừa <entity name='sdkmessage'>4; DeployPackageAsync nhánh no-op không gán PluginPackageId (B04 trong phân tích 29/09). Không chặn đề xuất này nhưng nên sửa cùng đợt.

8.2 Thuật toán deploy cho mỗi component

  1. Preflight (trước mọi mutation): GUID đúng định dạng; không trùng GUID trong cùng loại; PluginTypeId nhất quán trong một class; với nuget cảnh báo nếu có PluginTypeId/assembly Id (không áp dụng được).
  2. Lookup theo GUID (nạp cache bằng cả id in (...), không chỉ theo tên).
  3. Không thấy → lookup theo khoá tự nhiên như hiện nay.
  4. Không thấy cả hai → Create với GUID chỉ định (đặt pluginassemblyid/plugintypeid/sdkmessageprocessingstepid/sdkmessageprocessingstepimageid/pluginpackageid trên Entity). Nếu attribute không có GUID: dùng GUID tất định (tuỳ chọn C) hoặc để server sinh.
  5. Thấy theo tên nhưng GUID khác → drift, xử lý theo §09.
  6. Thu thập mọi GUID đã dùng/tạo vào báo cáo deploy (JSON) — đầu vào cho bước ghi ngược.

8.4 Solution ở môi trường đích

Giữ hành vi hiện tại (báo lỗi nếu solution không tồn tại) là an toàn nhất. Có thể bổ sung sau một tuỳ chọn tạo solution khi thiếu, nhưng cần chốt publisher (uniquename/prefix) phải giống DEV — prefix sai sẽ ảnh hưởng tên package và data source (SolutionPrefix được dùng trong DeployPackageAsync, IsValidDataProviderAsync).

10. Ghi ngược GUID vào CrmPluginRegistration

Lựa chọn 1 — VSIX

Mở rộng CommandAddCrmPluginRegistration: đọc DEV, chèn PluginTypeId, Id, ImageNId, attribute cấp assembly.

+ Đã có sẵn khung, dùng EnvDTE CodeModel.
− Chỉ trên Visual Studio, theo từng class; không chạy trong CI/AI agent; regex theo chuỗi dễ vỡ.

Lựa chọn 2 — CLI + Roslyn

Sau khi deploy DEV, CLI dùng báo cáo GUID, tìm class theo FullName trong thư mục source, khớp attribute theo tên step, chèn named argument.

+ Một lệnh cho cả project, chạy được với AI/CI.
− Thêm dependency Microsoft.CodeAnalysis.CSharp (CLI hiện chưa có); phải giữ formatting và hỗ trợ partial/nhiều file.

Lựa chọn 3 — Báo cáo JSON + áp dụng riêng

CLI luôn xuất ids.json; bước áp dụng do VSIX, AI agent, hoặc lệnh riêng thực hiện.

+ Tách deploy (ghi Dataverse) khỏi sửa source; dễ test.
− Thêm một bước.

Đề xuất: CLI luôn xuất báo cáo GUID (Lựa chọn 3) làm hợp đồng chung; sau đó cung cấp lệnh ghi ngược dựa trên Roslyn (Lựa chọn 2) và cập nhật VSIX dùng cùng báo cáo. Ghi ngược phải là hành động tường minh (cờ/lệnh riêng), không tự sửa source khi deploy UAT/TEST.

Không ghi SecureConfiguration lấy từ môi trường vào source khi ghi ngược. VSIX hiện đã chèn secure config từ DEV vào attribute (dòng 414–416) — đây là rủi ro lộ bí mật cần xem lại, độc lập với chuyện GUID.

11. Giới hạn và rủi ro

  • Plugin package: GUID assembly/type do platform tạo khi upload package; chỉ kiểm soát được package/step/image. Nếu dùng Custom API với nuget, phải bảo đảm Custom API tới UAT không mang lookup type của DEV (ví dụ để CLI bind sau theo uniquename — đúng cách DeployCustomApiStepAsync đang làm).
  • Thứ tự deploy: table/column phải có ở UAT trước khi deploy plugin (filtering attributes, image attributes, Custom API). Solution dữ liệu nên import trước devkit server.
  • Cấu hình theo môi trường: UnSecureConfiguration, SecureConfiguration, RunAs (tìm user theo tên ở môi trường đích), managed identity app ID đang nằm cố định trong source. Đổi connection mà không đổi các giá trị này có thể sai ở UAT/TEST. Đề xuất cơ chế override theo profile/.env ở giai đoạn sau.
  • Môi trường đã có dữ liệu cũ: UAT/TEST từng được import solution từ DEV thì GUID đã giống DEV — tốt. Nếu từng đăng ký tay bằng Plugin Registration Tool thì sẽ drift; cần chạy báo cáo drift trước khi chuyển quy trình.
  • Đổi tên step: với GUID tường minh, đổi tên giữ nguyên record (tốt). Với GUID tất định theo tên, đổi tên tạo record mới → step cũ cần được dọn.
  • Xoá component: TaskServer hiện không tự xoá step đã bỏ khỏi code (chỉ Unregister theo type). Đồng nhất GUID không giải quyết dọn rác giữa các môi trường.

  1. Ghi ngược GUID ưu tiên ở đâu: CLI (chạy được trong AI/CI) hay VSIX trước?

  6. Cấu hình theo môi trường (unsecure/secure config, RunAs, managed identity) có đưa vào cùng đợt không?
