01 / Kết luận để ra quyết định

Nên làm một sản phẩm mới, bắt đầu bằng một workflow hoàn chỉnh

Đề xuất: extension TypeScript độc lập + template assets mới + Dataverse Web API trực tiếp. Không bắt buộc cài DevKit CLI, không gọi Shared, không cần VSIX hoặc Visual Studio để tạo và triển khai một plugin cơ bản.

Extension: khả thi

Commands, explorer, chọn environment, wizard, form nhiều trường, preview, tiến độ và log đều có bề mặt phù hợp trong VS Code.

net48: build được

SDK-style library + .NET SDK + reference assemblies là cơ sở chính thức để biên dịch .NET Framework trên hệ điều hành khác Windows.

Debug: có giới hạn

VS Code không có hỗ trợ debugger .NET Framework tương đương Visual Studio. Không hứa chạy F5 plugin net48 trên Mac/Linux.

Căn cứ: Webview API, Microsoft reference assemblies, C# Dev Kit FAQ. Các quyết định thiết kế bên dưới là đề xuất cho DevKit, không phải tính năng đã tồn tại.

Phạm vi phù hợp với mục tiêu của bạn: người dùng Mac/Linux tạo C# plugin, build DLL, đăng ký vào Dataverse Online, kích hoạt nghiệp vụ trên server và đọc trace từ VS Code. Chuỗi này không đòi hỏi CLR .NET Framework chạy trên Mac/Linux.

02 / Câu hỏi quan trọng nhất

Tạo project plugin .NET 4.8 trên Mac/Linux: được đến đâu?

Nên gọi chính xác là .NET Framework 4.8, TFM net48. Tại thời điểm nghiên cứu, trang Supported customizations của Dataverse hỗ trợ plugin/custom workflow target .NET Framework 4.6.2–4.8 và khuyến nghị project mới dùng 4.8. Trang này cũng nêu assembly target .NET Core không được hỗ trợ cho plugin/custom workflow. Đây là căn cứ mạnh hơn việc suy từ target net462 của template DevKit hiện tại. Ví dụ: một .NET SDK hiện đại có thể chạy compiler trên Mac và dùng bộ reference assemblies net48 để tạo DLL. DLL không cần được load hoặc chạy trong process Node của extension. Dùng SDK 10 để build cũng không có nghĩa output trở thành plugin net10.0.

Còn unit test và trải nghiệm C#?

ĐỀ XUẤT Tách business logic ít phụ thuộc platform thành thư viện có target tương thích cả plugin và test host hiện đại, sau khi kiểm tra dependency cụ thể. Test logic đó trên macOS/Linux; giữ integration test qua Dataverse để kiểm chứng event pipeline. Những test thực sự cần CLR net48 vẫn cần môi trường Windows phù hợp. Test logic trên .NET mới không chứng minh tương đương toàn bộ sandbox/plugin context.

Không lấy “C# Dev Kit đã load được project” làm tiêu chí hoàn thành. Microsoft nêu giới hạn .NET Framework trong FAQ và hướng sử dụng C# extension. Cần thử đúng project đã chọn với completion, references, navigation, build diagnostics; nếu chưa ổn thì mô tả rõ mức hỗ trợ của bản DevKit đầu tiên. [C# Dev Kit FAQ]

03 / Thiết kế project mới

Template plugin net48 nên đơn giản và ít phụ thuộc OS

Kiểm tra template hiện có trong repo cho thấy server project đang là SDK-style net462, có signing, .snk, .projitems và các thao tác triển khai cũ. Đây chỉ là dữ kiện tham khảo. Với sản phẩm mới, đề xuất bắt đầu bằng một C# class library độc lập, dependency tường minh, không phát sinh .bat hoặc yêu cầu Visual Studio targets.

Bằng chứng repo: ProjectTemplates/CSharp/04.ServerProjectTemplate/ProjectTemplate.csproj.template; package project hiện tại ở ProjectTemplates/CSharp/05.PackageProjectTemplate. Đây là các đường dẫn tương đối từ thư mục v5; templates nằm cạnh component VSIX. Không có file source nào được sửa.

Hình dạng .csproj đề xuất — chỉ minh họa

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net48</TargetFramework>
    <OutputType>Library</OutputType>
    <PlatformTarget>AnyCPU</PlatformTarget>
    <SignAssembly>true</SignAssembly>
    <AssemblyOriginatorKeyFile>keys/Contoso.Plugins.snk</AssemblyOriginatorKeyFile>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Microsoft.NETFramework.ReferenceAssemblies"
                      Version="1.0.3" PrivateAssets="all" />
    <PackageReference Include="Microsoft.CrmSdk.CoreAssemblies"
                      Version="9.0.2.60" />
  </ItemGroup>
</Project>

Đây là snippet nghiên cứu, chưa phải template đã build. 9.0.2.60 là mốc package trong DynamicsCrm.DevKit.Vsix/DynamicsCrm.DevKit.Vsix.csproj và DynamicsCrm.DevKit.Shared/NuGetHelper.cs, không khẳng định là bản mới nhất hoặc đã xác nhận cho baseline mới. Cần pin lại sau PoC; file private key phải thực sự tồn tại. Không thêm package workflow nếu chỉ tạo plugin IPlugin. Không thay version của bất kỳ source hiện có nào.

NuGet reference assemblies cung cấp các hợp đồng compile-time, không cung cấp CLR để chạy net48. Tài liệu Microsoft cũng lưu ý SDK-style project có thể tự thêm reference package; khai báo explicit ở đây giúp thể hiện và pin dependency của template. [Build without an installed targeting pack]

# Lệnh minh họa do extension có thể gọi qua process/task API
# Chưa chạy trong nghiên cứu này
dotnet restore Contoso.Plugins.csproj
dotnet build Contoso.Plugins.csproj --configuration Release

# Output dự kiến: bin/Release/net48/Contoso.Plugins.dll
# Extension đọc bytes và gọi Dataverse Web API để triển khai.
Không dùng dotnet new classlib -f net48 như một giả định. Template classlib có sẵn chỉ nhận các target mà template/SDK đó hỗ trợ. Hướng mới này tự sinh .csproj net48 từ assets của DevKit; nếu muốn dùng dotnet new thì phải cung cấp custom template phù hợp. [dotnet new]

ĐỀ XUẤT Một package extension, một codebase TypeScript, chia module nội bộ theo trách nhiệm. Chưa cần tách thành nhiều npm package hoặc tạo service backend. Các assets C#/JS là nội dung template được đóng gói cùng extension.

Ranh giới nên giữ

  • domain không import VS Code API, không phụ thuộc giao diện.
  • Webview gửi request có kiểu; extension host xác thực request rồi thực thi.
  • Dataverse client chỉ xử lý transport/auth/serialization; nghiệp vụ registration ở module riêng.
  • Generator tạo kế hoạch file trước khi ghi; deployment engine tạo kế hoạch remote trước khi apply.

Dependencies hợp lý

  • VS Code API và Node runtime của extension host.
  • Thư viện MSAL Node cho identity.
  • .NET SDK khi người dùng build C# project.
  • npm/TypeScript toolchain của project người dùng nếu họ build web resources TS.
  • Không yêu cầu DevKit CLI, Shared hoặc cài Visual Studio.

Gọi Dataverse trực tiếp bằng TypeScript

Dataverse Web API cho phép truy cập từ ngôn ngữ hỗ trợ HTTP có xác thực. Vì vậy extension có thể dùng HTTP client trong Node để đọc metadata, thao tác record, gọi action/function và triển khai các thành phần có API tương ứng. Không cần bọc ServiceClient trong một process C# chỉ để thực hiện CRUD. Tuy nhiên phải kiểm tra endpoint cho từng tính năng; Web API không đồng nghĩa mọi tiện ích của SDK .NET đã có wrapper TS. [Dataverse Web API overview]

Không gọi Xrm.WebApi từ extension host. Đối tượng đó thuộc môi trường model-driven app. Phần extension mới dùng Web API qua HTTPS; code JS được generator sinh cho form có thể dùng API client của model-driven app theo mục đích của nó.

Authentication cũng viết mới, nhưng dùng thư viện identity chuẩn

ĐỀ XUẤT MSAL Node public client, ưu tiên authorization code + PKCE qua browser, silent acquisition cho phiên còn hiệu lực; device code là phương án bổ sung nếu chính sách tenant cho phép. Cần app registration của sản phẩm hoặc cấu hình client ID do tổ chức cung cấp, redirect URI và quyền Dataverse phù hợp. Không nhúng client secret vào extension phát hành, không lấy client ID mẫu làm danh tính sản phẩm. [MSAL Node flows] [Dataverse OAuth]

Thiết kế cache adapter tích hợp SecretStorage; chỉ lưu environment URL, tenant/client ID và lựa chọn project trong config thường. Không đưa token vào webview, output log hoặc file project. Tách tài khoản và environment để tránh dùng nhầm token khi chuyển tổ chức. Remote/SSH cần thử riêng callback đăng nhập và nơi lưu secrets; không suy từ đăng nhập local thành hỗ trợ remote hoàn chỉnh. [SecretStorage]

Desktop trước, remote sau, browser sau cùng

Đề xuất bản đầu là Node extension chạy trong workspace extension host; khi workspace ở SSH/container thì compiler và file operations phải chạy ở host chứa workspace. VS Code có hướng dẫn riêng cho remote extension. VS Code for the Web có runtime hạn chế và không thể được coi như môi trường có sẵn local process để chạy dotnet. Vì vậy “Mac/Linux desktop” là một cam kết khác “vscode.dev build C# trong browser”. [Remote extensions] [Web extensions]

Extension VS Code cũng có thể đóng gói thành file .vsix, nhưng package và host khác Visual Studio VSIX. Hướng JS thuần giúp đơn giản hóa phân phối; thêm binary/native module sau này sẽ phải quản lý OS/architecture riêng. [Publishing extensions]

05 / Backend plugin hoàn toàn mới

Không cần CLR reflection cho luồng “project do DevKit tạo”

Đây là điểm quyết định để giữ backend thuần TypeScript. Một extension Node không tự có Assembly.Load hay reflection .NET. Với project được tạo mới, DevKit có thể sinh đồng thời source plugin và manifest đăng ký, rồi dùng manifest để biết type, message, table, stage, mode và images.

Chọn manifest-first cho bản đầu. Cấu hình registration là dữ liệu có schema, có review và diff. Extension không cần load/execute DLL của người dùng để tìm lớp plugin. Việc đọc metadata từ DLL bất kỳ là một tính năng mở rộng có chi phí riêng.

Luồng triển khai đề xuất

  1. Create Project: tạo project net48, source IPlugin, cấu hình build và manifest mới. Người dùng có thể làm bước này offline.
  2. Add Plugin / Step: chọn message, table, stage, mode và attributes từ metadata của environment đang kết nối; sinh class và cấu hình liên quan.
  3. Build: gọi dotnet, đọc diagnostics, xác định đúng output DLL của project/configuration; dừng nếu build thất bại hoặc artifact không đúng.
  4. Plan: so sánh manifest, identity assembly và trạng thái server; hiện assembly/type/step/image sẽ được tạo hoặc cập nhật.
  5. Deploy: upload/update assembly, đọc trạng thái type, tạo/cập nhật registration phù hợp; bổ sung vào solution theo loại component.
  6. Verify: đọc lại các record đã triển khai, lưu mapping ID theo environment, cung cấp cách kích hoạt event và xem trace.

Nếu người dùng đưa vào DLL bất kỳ?

ĐỀ XUẤT Bản đầu yêu cầu khai báo type hoặc dùng wizard tạo type cùng source. Về sau có thể đọc ECMA-335 metadata bằng implementation/thư viện TS đã thẩm định để discover types/attributes. Một helper .NET sẽ đơn giản hóa phần này, nhưng trở thành quyết định thay đổi ranh giới “mọi logic mới bằng TS”. Không cần đưa helper đó vào kiến trúc khởi đầu.

Không dùng regex đọc C# làm nguồn chân lý cho type trong DLL: namespace, partial class, generated source, conditional compilation và attribute semantics khiến cách đó thiếu tin cậy. Không cần chạy DLL để đọc metadata; đặc biệt không chạy assembly người dùng trong host của extension.

Độ khó thật nằm ở cập nhật an toàn và kết quả có thể lặp lại

  • Idempotency: chạy deploy hai lần không tạo step trùng. Mapping server ID phải gắn với environment và logical key; không nhận diện chỉ bằng display name.
  • Partial failure: server có thể nhận assembly nhưng bước tạo step thất bại. Hiển thị trạng thái từng bước và cách tiếp tục; không hứa rollback atomic cho cả deployment.
  • Timeout/retry: xử lý throttling theo Retry-After; khi POST timeout phải reconcile trước khi gửi lại để tránh tạo trùng. [Service protection limits]
  • Update identity: thay version, key hoặc bỏ type đang được step sử dụng cần kế hoạch rõ; không tự xóa hàng loạt để “đồng bộ”.
  • Scope: MVP chỉ Dataverse Online + plugin sandbox + bộ registration cơ bản. Custom workflow, on-premises và plugin package là các phạm vi bổ sung.

Những chi tiết thường làm template hỏng trên Mac/Linux

  • Path: dùng URI/path API, không nối bằng dấu \; hỗ trợ khoảng trắng, Unicode và filesystem phân biệt hoa/thường.
  • Process: truyền executable và argument array, dùng process execution; không tạo chuỗi lệnh cmd.exe hoặc giả định có PowerShell.
  • File ownership: đánh dấu file generated và file user-owned. Regenerate không ghi đè business code người dùng đã sửa.
  • Rollback cục bộ: plan và staging trước; nếu ghi một phần thất bại chỉ cleanup file do operation đó tạo, tránh xóa file đã tồn tại.
  • Project discovery: chọn project theo thông tin thực tế thay vì giả định có một solution đang mở như Visual Studio.
  • Template version: record version để biết project được sinh bằng template nào; nâng cấp output là luồng có preview riêng.

VS Code Task Provider có thể tích hợp build tasks và diagnostics. Workspace Trust cần được xét trước khi chạy process hoặc task từ workspace; cho phép đọc/scaffold ở phạm vi hợp lý và chỉ chạy hành động nhạy cảm theo trạng thái trust. [Task Provider] [Workspace Trust]

  • Metadata volume: môi trường lớn cần pagination/cache và cancellation, không tải tất cả mỗi lần mở wizard.
  • Template compatibility: viết mới cho phép schema mới; nếu tương lai muốn mở project cũ, đó là scope bổ sung, không được tính là miễn phí.
  • Claim parity: full report designer, debugger và semantic analyzers có chi phí khác hẳn form CRUD.
