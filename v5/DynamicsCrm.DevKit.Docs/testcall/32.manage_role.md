# 32. manage_role

# Tool description AI đọc được

```
Security roles — list/detail/user/assign/unassign/create/update/delete/copy.
- list: optional role_name, business_unit_id, max_records
- detail: role_id OR role_name (+optional entity_name) → privileges grouped by entity. Resolves role name first (fuzzy), then GUID fallback.
- user: user_id (+optional entity_name) → user's roles + effective privileges
- assign / unassign: role_id + user_id (direct) or team_id (role for a team; members inherit it). user action also reports roles inherited via team membership.
- create: role_name (+optional business_unit_id)
- update: role_id + optional role_name (rename) and/or privileges (JSON array of {entity, right, depth}) to add/change/remove privileges and depth on an existing role. Depth: User | BusinessUnit | Parent:ChildBU | Organization; 'None' removes. Rights: Create | Read | Write | Delete | Append | AppendTo | Assign | Share, or '*' to apply to all rights of the entity.
- delete: role_id (irreversible; managed roles can't delete — use copy)
- copy: role_id + role_name (clone with all privileges)
Mutating actions require the System Administrator role on the calling user.

Depth: User < BU < Parent:ChildBU < Org. Only root roles listed (not BU-inherited copies). Fuzzy on role_name: 0/multi → tool returns disambiguation list and stops; AI must ask user. 1 → auto.

WHEN TO USE:
- Debug 'access denied' (action='user' + entity_name)
- Audit role privileges (action='detail')
- Provision access (assign/unassign or create/copy)
RELATED TOOLS: whoami, manage_record, execute_fetchxml.
```

Input schema params: `action` (required), `user_id`, `team_id`, `role_id`, `role_name`, `business_unit_id`, `entity_name`, `privileges` (JSON string), `max_records` (default 50).

Runtime proof: build `17.08.2026 10:28:32`, assemblySha256 `7C44A125390B1C908EAF9570558F735C7A34CF4F87CC11A3AEE6FE1C2AC870DB` khớp build-manifest. Môi trường 🟢DEVKITV4, solution `all_in_one`. Dry-run KHÔNG test (refactor3 §0 — không truyền được setting khi MCP run). Không đụng table `all_in_one`. Schema đổi: refactor refactor3 (đã commit `ec1f2592b`), bổ sung `update` + `privileges` JSON (add/đổi depth/remove/wildcard `*`), `assign`/`unassign` chấp nhận `team_id`, `user` action thêm `rolesViaTeams` + effective privileges gộp team.

# Kết quả AI tổng hợp

- **Refactor refactor3** (commit `ec1f2592b`): 1 try-catch entry, factory methods trực tiếp, E2E null-aware theo rule 4, gate qua RoleGateHelper ở rule 12, Hint: label chuẩn. Bug discovered: cũ nhầm nhiều user/role match thành multi-line Success — đã fix thành Error kèm details trong tool này (và làm gương cho tool khác).
- **Tính năng mới của `update` (Test 5–12)**: 1 đường `privileges` JSON atomic, hỗ trợ add/đổi depth/remove đơn lẻ và wildcard `right:"*"` theo entity, dùng `ReplacePrivilegesRoleRequest` (không phải gỡ rồi add) để giữ nguyên depth mask gốc của các privilege không đụng đến — quan trọng cho misc privileges không lộ trong tool.
- **Tính năng mới của `assign`/`unassign` + `team_id` (Test 17–22)**: gán role cho team qua `teamroles_association`, member team inherit — chính là screen "Teams → Manage Roles" trong portal Dataverse. Test 19 xác minh `rolesViaTeams` xuất hiện đúng khi gán, Test 22 xác minh null khi gỡ (field biến mất theo rule 4).
- **Bug fix correctness của action `user`**: trước đây `effectivePrivileges` chỉ tính role direct, bỏ qua thừa kế qua team — user có quyền do team cấp sẽ bị báo "missing" hết. Bây giờ gộp cả 2 nguồn (direct + via team), consistency với Dataverse UI.
- **Không touch rule 8 (execute_webapi)**: tool đã redirect `roles(*)` GET + POST sang `manage_role` từ trước — `execute_webapi` không cần đổi.
- **Quan sát**: Dataverse tự thêm ~9 default SDK/SharePoint Read privileges (depth=Organization) cho role mới tạo. Đây là behavior chuẩn của Dataverse (business unit root role template), không phải bug tool — AI debug "role rỗng nhưng có 10 privileges" cần nhớ fact này.
- **Bộ nhớ 5 đề xuất từ giai đoạn phân tích**: đã xử lý 2 (`update` privileges + team support). Đề xuất 1 (copy privilege chéo giữa 2 role có sẵn) và 5 (create role mới từ template) — pattern hiện tại (copy + update riêng) đã cover use case, có thể bỏ qua. Đề xuất tương lai nếu cần: mở rộng `copy` thêm `target_role_id` + `entity_name` filter.
