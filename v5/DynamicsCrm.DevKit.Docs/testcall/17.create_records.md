# 17. create_records

# Tool description AI đọc được

```text
Name:        create_records
Title:       Bulk create Dataverse records in parallel (max 5000/call)
Idempotent:  false
Destructive: false
ReadOnly:    false

Description:
Bulk create Dataverse records in parallel (max 5000/call). Partial failures: successes committed, failures reported per-item. Input: inline JSON array, .json path, or .csv path (Display Name headers).

WHEN TO USE:
- Seed many records at once (accounts, contacts, tasks) or import from CSV
- Pipe generate_demo_data output file (.json) into records_json
- High-throughput parallel creates (server hints concurrency when max_parallelism=0)

RELATED TOOLS:
- generate_demo_data → produce JSON to pipe into create_records
- manage_record → single-record create/update/delete/associate/disassociate
- search_records / execute_fetchxml → verify created records

Field syntax: polymorphic lookup 'field@targetentity' (e.g. 'customerid@account'); activity parties (to/from/cc/bcc/requiredattendees/organizer/customers/resources) are a JSON array of {"id":"<guid>","type":"<entity>"} (single object auto-wrapped; do NOT set participationtypemask). For single-record CRUD → manage_record.

BYPASS: bypass_custom_logic=true sets BypassBusinessLogicExecution=CustomSync,CustomAsync so sync+async plugins/workflows do NOT run for this create. Default false. Requires the System Administrator role (prvBypassCustomBusinessLogic privilege); rejected early if the calling user lacks it. Use for bulk seed/data-load where custom logic would slow or block creates.
```

## Key behaviors verified

### Input formats & parallelism

- **3 input formats** auto-detected and reported in `inputFormat`: `inline-json`, `json-file`, `csv`
- **Default parallelism = 4** from server `x-ms-dop-hint` (hard limit 52); explicit `max_parallelism=1` suppresses warning + sets `usedDefaultParallelism:false`

### Field syntax (refactor3.md §1: Field syntax)

- **Polymorphic lookup** `<field>@<targetentity>` resolves target entity from metadata. Verified on:
  - `primarycontactid@contact` (1:N single-target — Test 4)
  - `parentcustomerid@account` AND `parentcustomerid@contact` (Customer polymorphic, 2 targets in same field — Test 12)
  - `ownerid@systemuser` (Polymorphic on Task — Test 14, 16, 18)
  - `regardingobjectid@account` AND `regardingobjectid@contact` (Polymorphic on Task/PhoneCall — Tests 14, 16, 18, 19)
- **Activity party** `from` / `to` use `{id,type}` object form (auto-wrapped to single-party) OR JSON array form (multi-recipient):
  - Single object → single party (Tests 16, 18 sender side)
  - Array → multi party (Tests 16, 18 recipient side)
  - Sender (`from`) on PhoneCall: server enforces ≤1 sender (Test 17)
  - Activity-party syntax is **parser-accepted** on any activity entity; **field-existence** is checked per-record (Test 15 demonstrates rejection on Task)
- **Do NOT set `participationtypemask`** — Dataverse sets it from field name automatically (verified in tests, never set explicitly)

### Bulk partial-failure semantics (refactor3.md §3.13)

- `total`, `succeeded`, `failed` always present
- `items[]` carries per-record outcome (`status:"created"` with id OR `status:"failed"` with `id:""` + error)
- `id` field **always present** in every item — GUID for created records, `""` for failed records
- `status:"partial"` when some succeeded, `status:"failed"` when all failed, `status:"created"` when all succeeded
- `IsError:true` for both `partial` and `failed` — signals to MCP client that not all records succeeded
- `IsError:false` only when `status:"created"` (all succeeded) or pre-flight `Error(...)` (validation errors)
- Dataverse errors pass through verbatim (Test 17 multi-sender rule, Test 5 max-length rule)
- **No `failedItems[]` duplication** — failed items are inline in `items[]` with `id:""` + `status:"failed"` + `error`

### CSV header mapping

- Case-insensitive Display Name → logical name (`Website`→`websiteurl`, `ImportSequenceNumber`→`importsequencenumber`, `Telephone1`→`telephone1`, `Revenue`→`revenue`)
- **Duplicate CSV header fast-fail**: two columns resolving to the same logical name → `InvalidOperationException` before any records are processed
- **Ambiguous CSV header fast-fail**: a header matching multiple fields by Display Name → `InvalidOperationException` listing all candidates
- Activity-party / polymorphic-lookup columns in CSV not tested (they require `@targetentity` syntax which CSV headers don't support); use `.json` or inline JSON for those

### JSON field name validation

- **Case-insensitive** field name resolution: `WebsiteUrl`, `websiteurl`, `WEBSITEURL` all resolve to `websiteurl`
- **Duplicate JSON field fast-fail**: two keys resolving to the same logical name (e.g. `websiteurl` + `WebsiteUrl`) → per-record `ArgumentException` with clear error message + Tip

### Validation taxonomy (returns `Error(...)` with `IsError:true`)

- Unknown entity: `[NotFoundEntity]` + Tip → `get_tables`
- Malformed input (not a JSON array): `records_json must be a JSON array.`
- File not found: `File not found: <path>`
- Empty array: `records_json array is empty.`
- CSV duplicate header: `CSV header '...' (column N) maps to field '...', but a previous column already maps to the same field.`
- CSV ambiguous header: `[AmbiguousField] Multiple candidates match '...'` + candidate list

### Per-record validation (returns `items[]` with `id:""` + `IsError:true`)

- Unknown field: `[NotFoundField]` + Tip → `get_tables`
- Duplicate JSON field: `fields_json key '...' resolves to field '...', but a previous key already resolved to the same field.`
- Dataverse server-side rules: e.g. `name` > 160 chars (Test 5), `from` array on PhoneCall (Test 17), field-not-on-entity (Tests 13, 15)

### Cleanup & propagation

- After `manage_record(action='delete', ...)`, FetchXML may briefly return leftover records (async propagation). After ~5s wait, queries return 0 — Dataverse read-after-write behavior, not a tool bug
