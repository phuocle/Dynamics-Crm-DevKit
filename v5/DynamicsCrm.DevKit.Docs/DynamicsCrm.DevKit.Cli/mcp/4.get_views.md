# Proposal: get_views MCP Tool

## Priority: 4 (UI Customization -- Views are the #2 UI artifact)

## Why This Tool Is Needed

Views define how data is displayed in lists/grids. Every entity has system views (Active, Inactive, My Active, Quick Find, Lookup, Associated). Currently AI cannot read view definitions (FetchXML query + LayoutXML columns) to understand what data is shown or help customize views.

Only **Greg.Xrm.Mcp (AppMaker)** has view tools (5 tools: inventory, get, update, create, rename).

## Purpose

Retrieve view (saved query) definitions for a Dataverse entity. Two modes:
1. **List mode** (no `view_id`) -- list all views for an entity with name, type, status
2. **Detail mode** (with `view_id`) -- get full FetchXML, LayoutXML, and metadata

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | - | Entity logical name (e.g., `"account"`). |
| view_id | string | No | (empty) | GUID of a specific view. Leave empty to list all views. |
| query_type | int | No | (empty) | Filter by view type: `0` = Public, `1` = Lookup, `2` = AdvancedSearch, `4` = QuickFind, `64` = SubGrid. Leave empty for all. |
| include_fetchxml | bool | No | false | In list mode: also include FetchXML/LayoutXML for each view. In detail mode: always included. |
| include_personal | bool | No | false | Also include personal views (`userquery` table) owned by current user. Default: only system views. |

## Dataverse Tables

**System views:** `savedquery` | **Entity Set:** `/savedqueries`
**Personal views:** `userquery` | **Entity Set:** `/userqueries`

### Key Columns (savedquery)

| Column | Type | Description |
|--------|------|-------------|
| `savedqueryid` | Guid | Primary key |
| `name` | String | View display name |
| `returnedtypecode` | String | Entity logical name |
| `querytype` | Int | View type (0=Public, 1=Lookup, 2=AdvancedSearch, 4=QuickFind, 64=SubGrid) |
| `fetchxml` | Memo | FetchXML query definition |
| `layoutxml` | Memo | Column layout definition |
| `layoutjson` | Memo | Column layout in JSON format |
| `isdefault` | Boolean | Default view flag |
| `ismanaged` | Boolean | Managed view flag |
| `statecode` | State | 0 = Active, 1 = Inactive |
| `columnsetxml` | Memo | Column set XML (legacy) |
| `conditionalformatting` | Memo | Conditional formatting rules |
| `description` | String | View description |

### Query Type Values

| Value | Type | Description |
|-------|------|-------------|
| 0 | Public | Main views visible in the view selector |
| 1 | Lookup | Used in lookup dialogs |
| 2 | AdvancedSearch | Used by Advanced Find |
| 4 | QuickFind | Quick Find search view |
| 64 | SubGrid | Associated/sub-grid views |
| 131072 | Custom | Custom defined query types |

### FetchXML Query Pattern

```xml
<!-- List mode -->
<fetch>
  <entity name="savedquery">
    <attribute name="savedqueryid" />
    <attribute name="name" />
    <attribute name="querytype" />
    <attribute name="isdefault" />
    <attribute name="statecode" />
    <attribute name="ismanaged" />
    <attribute name="description" />
    <filter type="and">
      <condition attribute="returnedtypecode" operator="eq" value="account" />
      <condition attribute="statecode" operator="eq" value="0" />
    </filter>
    <order attribute="querytype" />
    <order attribute="name" />
  </entity>
</fetch>

<!-- Detail mode -->
<fetch>
  <entity name="savedquery">
    <all-attributes />
    <filter>
      <condition attribute="savedqueryid" operator="eq" value="{view_id}" />
    </filter>
  </entity>
</fetch>
```

## Tool Description for AI

```
Retrieve view (saved query) definitions for a Dataverse entity. Returns view
names, types, FetchXML queries, and LayoutXML column definitions.

PARAMETERS:
- entity_name (required): Entity logical name (e.g., 'account', 'contact').
- view_id: GUID of a specific view for full details. Leave empty to list all.
- query_type: Filter by type: 0=Public, 1=Lookup, 4=QuickFind, 64=SubGrid.
- include_fetchxml: Include FetchXML/LayoutXML in list mode (default: false).
- include_personal: Also include personal views (default: false, system views only).

RETURNS:
- List mode: Table of views with ID, name, type, default status
- Detail mode: Full FetchXML query + LayoutXML column layout + metadata

WHEN TO USE:
- To understand how data is displayed in an entity's grid/list
- To find which columns are shown in the default view
- To get the FetchXML query behind a view for analysis or modification
- Before modifying a view via execute_webapi
- To help users create or customize views

TIPS:
- querytype=0 (Public) views are what users see in the view selector
- querytype=4 (QuickFind) defines what columns are searched
- The default Public view (isdefault=true, querytype=0) is shown by default
- LayoutXML defines column order and widths in the grid
- To UPDATE a view: use update_view tool (auto-backup + sync validation + publish)
- update_view handles: backup current XMLs → validate → sync-check → update → publish
- DO NOT use execute_webapi for view updates — use update_view for safety
```

## CRITICAL: Backup Strategy Before View Modifications

> **WARNING:** Views have TWO XML parts (FetchXML + LayoutXML) that MUST stay in sync. A broken FetchXML hides all data. A broken LayoutXML shows wrong columns or crashes the grid. Restoring requires the EXACT original XML.

### Lesson from AppMaker (Greg.Xrm.Mcp)

AppMaker's `UpdateViewDefinition` tool directly overwrites LayoutXML/FetchXML without backup. Their `UpdateSiteMap` says: "Before applying any update, BE SURE to retrieve the latest version." This means they rely on AI discipline rather than automated backup -- a risky approach.

### DevKit Backup Approach

DevKit should implement **explicit backup instructions** in tool descriptions, and when a future `update_view` tool is built, it should auto-backup.

#### Backup Instructions for AI (via tool description):

**Use the dedicated `update_view` tool (#12)** instead of manual execute_webapi calls:

```
SAFE VIEW MODIFICATION WORKFLOW:
1. Call get_views with view_id to READ current FetchXML + LayoutXML
2. Modify the XMLs as needed (follow docs://instructions_for_views rules)
3. Call update_view with the modified XMLs
4. update_view auto-handles: backup → validate → sync-check → update → publish
5. If view breaks: use the backup file paths from update_view response to rollback
```

**DO NOT use `execute_webapi` for view updates** — always use `update_view` which provides:
- Auto-backup of BOTH FetchXML + LayoutXML before overwriting
- FetchXML↔LayoutXML sync validation (every attribute must have a cell)
- XSD validation against LayoutXml.xsd and Fetch.xsd
- Auto-publish after update
- Rollback instructions in response

See `12.update_view.md` for full specification.

#### Rollback Procedure

```
1. Read the backup files
2. PATCH /savedqueries({viewid}) with body: {"fetchxml": "<original>", "layoutxml": "<original>"}
3. Call publish_customizations for the entity
4. Verify view loads correctly
```

### Backup File Location

```

  account_abc123_20260329180000.layoutxml.bak
```

## Implementation Notes

- Query `savedquery` table using FetchXML (system views)
- Optionally query `userquery` table for personal views (separate query, merge results)
- Map query type integers to display names
- FetchXML and LayoutXML can be verbose -- in list mode, only include if `include_fetchxml=true`
- Filter by `statecode eq 0` (active views only) by default
- Pretty-print XML in detail mode for readability
