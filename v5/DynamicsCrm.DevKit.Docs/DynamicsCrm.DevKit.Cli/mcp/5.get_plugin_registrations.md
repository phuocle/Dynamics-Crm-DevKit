# Proposal: get_plugin_registrations MCP Tool

## Priority: 5 (Plugin Development -- Essential for understanding event pipeline)

## Why This Tool Is Needed

Plugin development is a core Dynamics 365 developer workflow. AI needs to understand the existing event pipeline -- what plugins are registered, on which messages, with what step configuration, and what images are attached. Currently AI has NO way to query this information.

The Plugin Registration Tool is the **most-used standalone developer tool** in the Dynamics 365 ecosystem. Exposing this data via MCP enables AI to assist with plugin development, troubleshooting, and auditing.

## Purpose

Query registered plugin assemblies, types, steps, and images for a specific entity or across the entire environment.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | No | (empty) | Filter by entity logical name (e.g., `"account"`). Leave empty for all entities. |
| assembly_name | string | No | (empty) | Filter by plugin assembly name (contains match, e.g., `"MyPlugins"`). |
| message_name | string | No | (empty) | Filter by SDK message (e.g., `"Create"`, `"Update"`, `"Delete"`). |
| include_images | bool | No | true | Include step images (Pre/Post entity images). Default: true. |
| max_records | int | No | 100 | Maximum steps to return. Default: 100. |

## Dataverse Tables

| Table | Entity Set | Purpose |
|-------|-----------|---------|
| `pluginassembly` | `/pluginassemblies` | Assembly DLLs registered in Dataverse |
| `plugintype` | `/plugintypes` | Individual plugin classes within assemblies |
| `sdkmessageprocessingstep` | `/sdkmessageprocessingsteps` | Event pipeline step registrations |
| `sdkmessageprocessingstepimage` | `/sdkmessageprocessingstepimages` | Pre/Post entity images on steps |
| `sdkmessage` | `/sdkmessages` | SDK message definitions (Create, Update, etc.) |
| `sdkmessagefilter` | `/sdkmessagefilters` | Message-to-entity filters |

### FetchXML Query Pattern

```xml
<fetch>
  <entity name="sdkmessageprocessingstep">
    <attribute name="sdkmessageprocessingstepid" />
    <attribute name="name" />
    <attribute name="stage" />
    <attribute name="mode" />
    <attribute name="rank" />
    <attribute name="filteringattributes" />
    <attribute name="statecode" />
    <attribute name="description" />
    <attribute name="asyncautodelete" />
    <attribute name="configuration" />
    <link-entity name="plugintype" from="plugintypeid" to="plugintypeid" alias="pt">
      <attribute name="name" />
      <attribute name="typename" />
      <attribute name="assemblyname" />
      <link-entity name="pluginassembly" from="pluginassemblyid" to="pluginassemblyid" alias="pa">
        <attribute name="name" />
        <attribute name="version" />
        <attribute name="isolationmode" />
      </link-entity>
    </link-entity>
    <link-entity name="sdkmessage" from="sdkmessageid" to="sdkmessageid" alias="msg">
      <attribute name="name" />
    </link-entity>
    <link-entity name="sdkmessagefilter" from="sdkmessagefilterid" to="sdkmessagefilterid" alias="flt" link-type="outer">
      <attribute name="primaryobjecttypecode" />
    </link-entity>
    <filter type="and">
      <!-- Add entity filter via flt.primaryobjecttypecode if entity_name provided -->
      <!-- Add assembly filter via pa.name if assembly_name provided -->
      <!-- Add message filter via msg.name if message_name provided -->
    </filter>
    <order attribute="name" />
  </entity>
</fetch>
```

### Step Images Query (separate query per step)

```xml
<fetch>
  <entity name="sdkmessageprocessingstepimage">
    <attribute name="name" />
    <attribute name="entityalias" />
    <attribute name="imagetype" />
    <attribute name="attributes" />
    <attribute name="messagepropertyname" />
    <filter>
      <condition attribute="sdkmessageprocessingstepid" operator="eq" value="{stepid}" />
    </filter>
  </entity>
</fetch>
```

## Response Format (Compact)

```
[PluginRegistrations] account (8 steps)

assembly	plugin	message	stage	mode	rank	filterAttr	status	images
MyPlugins v1.0	AccountPlugin	Create	PreValidation(10)	Sync	1	-	Active	Pre:Target
MyPlugins v1.0	AccountPlugin	Update	PreOperation(20)	Sync	1	name,revenue	Active	Pre:Target,Post:Target
MyPlugins v1.0	AccountPlugin	Delete	PreOperation(20)	Sync	1	-	Active	Pre:Target
OtherPlugins v2.1	AuditPlugin	Update	PostOperation(40)	Async	10	-	Active	Pre:PreImage,Post:PostImage
...
```

### Stage Values

| Value | Name |
|-------|------|
| 10 | PreValidation |
| 20 | PreOperation |
| 30 | MainOperation (internal) |
| 40 | PostOperation |

### Mode Values

| Value | Name |
|-------|------|
| 0 | Synchronous |
| 1 | Asynchronous |

### Image Type Values

| Value | Name |
|-------|------|
| 0 | PreImage |
| 1 | PostImage |
| 2 | Both |

## McpServerTool Attribute

```csharp
[McpServerTool(
    Name = "get_plugin_registrations",
    ReadOnly = true,
    Idempotent = true)]
```

## Tool Description for AI

```
Query registered plugin assemblies, types, steps, and images for Dataverse entities.
Shows the event pipeline: what code runs on which messages at which stages.

PARAMETERS:
- entity_name: Filter by entity (e.g., 'account'). Leave empty for all entities.
- assembly_name: Filter by assembly name (contains match, e.g., 'MyPlugins').
- message_name: Filter by SDK message ('Create', 'Update', 'Delete').
- include_images: Include Pre/Post entity images (default: true).
- max_records: Maximum steps to return (default: 100).

RETURNS:
- Table of plugin steps: assembly, plugin class, message, stage, mode,
  rank, filtering attributes, status, and attached images

WHEN TO USE:
- When developing a new plugin and need to understand existing registrations
- To check if a specific message/entity already has a plugin registered
- When debugging plugin execution order (check rank and stage)
- To audit what plugins run on an entity for security/performance review
- When troubleshooting plugin conflicts or duplicate registrations

TIPS:
- Stage 10=PreValidation, 20=PreOperation, 40=PostOperation
- Mode 0=Sync, 1=Async (async won't block the user)
- filteringattributes = empty means plugin runs on ALL attribute changes
- Use with get_plugin_trace_logs to debug plugin execution
- Lower rank = executes first (within same stage+message)
```

## Implementation Notes

- Main query on `sdkmessageprocessingstep` with joins to `plugintype`, `pluginassembly`, `sdkmessage`, `sdkmessagefilter`
- Step images require a separate query on `sdkmessageprocessingstepimage`
- For efficiency: batch image queries or use a single query with `in` operator for all step IDs
- Map stage/mode/imagetype integers to display names
- `filteringattributes` is comma-separated attribute list or null (means all attributes)
- Isolation mode: 1 = None (on-prem), 2 = Sandbox (cloud) -- include in assembly info
