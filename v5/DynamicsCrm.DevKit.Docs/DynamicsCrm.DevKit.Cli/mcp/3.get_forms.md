# Proposal: get_forms MCP Tool

## Priority: 3 (UI Customization -- Forms are the #1 UI artifact)

## Why This Tool Is Needed

Forms are the **primary UI** in model-driven apps. Every entity has at least one form, and customizing forms is one of the most common tasks. Currently, AI has NO way to:
- List what forms exist for an entity
- Read FormXML to understand the layout (tabs, sections, fields)
- Know which form is the default main form

Only **Greg.Xrm.Mcp (AppMaker)** has form tools among 15+ Dataverse MCP servers. DevKit should match and exceed this with compact output and better AI descriptions.

## Competitor Analysis (AppMaker)

AppMaker has 4 form-related tools:
1. **Form Inventory** -- list forms (text/JSON)
2. **Form Definition Retrieval** -- get FormXML/FormJSON
3. **Form Updater** -- modify form structure (write)
4. **FormXML Validation** -- validate against XSD

DevKit's `get_forms` combines #1 and #2 into a single tool (list mode + detail mode), following the same pattern as `get_global_optionsets` (list all vs get specific).

## Purpose

Retrieve form definitions for a Dataverse entity. Two modes:
1. **List mode** (no `form_id`) -- list all forms for an entity with name, type, status
2. **Detail mode** (with `form_id`) -- get full FormXML and metadata for a specific form

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | - | Entity logical name (e.g., `"account"`, `"contact"`). If unsure, call `get_entities_metadata` first. |
| form_id | string | No | (empty) | GUID of a specific form. Leave empty to list all forms for the entity. |
| form_type | int | No | (empty) | Filter by form type: `2` = Main, `5` = Mobile, `6` = QuickView, `7` = QuickCreate. Leave empty for all types. |
| include_formxml | bool | No | false | In list mode: also include FormXML for each form (increases output size). In detail mode: always included regardless. |

## Dataverse Table

**Entity:** `systemform` | **Entity Set:** `/systemforms`

### Key Columns

| Column | Type | Description |
|--------|------|-------------|
| `formid` | Guid | Primary key |
| `name` | String | Form display name |
| `objecttypecode` | String | Entity logical name (e.g., "account") |
| `type` | Int | Form type (see below) |
| `formactivationstate` | Int | 0 = Inactive, 1 = Active |
| `isdefault` | Boolean | Default form for this type |
| `description` | String | Form description |
| `formxml` | Memo | XML layout definition |
| `formjson` | Memo | JSON layout definition |
| `solutionid` | Guid | Solution the form belongs to |
| `ismanaged` | Boolean | Whether the form is managed |
| `publishedon` | DateTime | Last published date |
| `version` | Int | Form version number |

### Form Type Values

| Value | Type | Description |
|-------|------|-------------|
| 0 | Dashboard | Dashboard form |
| 2 | Main | Main entity form (most common) |
| 4 | Preview | Preview form |
| 5 | Mobile | Mobile Express form |
| 6 | QuickViewForm | Quick view form (embedded in other forms) |
| 7 | QuickCreate | Quick create dialog |
| 8 | Dialog | Dialog form |
| 11 | MainInteractive | Main Interactive Experience form |
| 12 | Other | Card form or other |

### FetchXML Query Pattern

```xml
<!-- List mode -->
<fetch>
  <entity name="systemform">
    <attribute name="formid" />
    <attribute name="name" />
    <attribute name="type" />
    <attribute name="formactivationstate" />
    <attribute name="isdefault" />
    <attribute name="description" />
    <attribute name="ismanaged" />
    <attribute name="publishedon" />
    <attribute name="version" />
    <!-- Only include formxml if include_formxml=true -->
    <filter type="and">
      <condition attribute="objecttypecode" operator="eq" value="account" />
      <condition attribute="formactivationstate" operator="eq" value="1" />
      <!-- Add type filter if form_type specified -->
    </filter>
    <order attribute="type" />
    <order attribute="name" />
  </entity>
</fetch>

<!-- Detail mode -->
<fetch>
  <entity name="systemform">
    <all-attributes />
    <filter>
      <condition attribute="formid" operator="eq" value="{form_id}" />
    </filter>
  </entity>
</fetch>
```

## Tool Description for AI

```
Retrieve form definitions for a Dataverse entity. Returns form names, types,
and optionally the full FormXML layout definition.

PARAMETERS:
- entity_name (required): Entity logical name (e.g., 'account', 'contact').
  Call get_entities_metadata first if unsure of the logical name.
- form_id: GUID of a specific form to get full details including FormXML.
  Leave empty to list all forms for the entity.
- form_type: Filter by type: 2=Main, 5=Mobile, 6=QuickView, 7=QuickCreate.
  Leave empty for all form types.
- include_formxml: In list mode, also include FormXML (default: false to save tokens).

RETURNS:
- List mode: Table of forms with ID, name, type, default status, activation state
- Detail mode: Full form metadata + complete FormXML layout definition

WHEN TO USE:
- To understand the UI layout of an entity before making customizations
- To find the form ID needed for form updates via execute_webapi
- To check which fields are on a form and how they are arranged
- To identify the default main form for an entity
- Before adding/removing fields from a form

TIPS:
- Most entities have multiple forms -- use form_type=2 to get only main forms
- The default main form (isdefault=true, type=2) is what most users see
- FormXML defines: tabs > columns > sections > rows > cells > controls
- Use include_formxml=false (default) for quick discovery, true for detailed analysis
- To UPDATE a form: use update_form tool (auto-backup + validate + publish)
- update_form handles: backup current XML → validate against XSD → update → publish
- DO NOT use execute_webapi for form updates — use update_form for safety
```

## CRITICAL: Backup Strategy Before Form Modifications

> **WARNING:** Modifying FormXML incorrectly can break forms completely, making entities unusable in the UI. A corrupted form may require environment restoration. ALWAYS backup before modifying.

### Lesson from AppMaker (Greg.Xrm.Mcp)

AppMaker's `docs://instructions_for_formxml` MCP Resource mandates:

> "Always create a copy of the form XML in the local workspace before making any changes."

Their backup file naming convention: `{TableSchemaName}_{FormId}_{yyyyMMddHHmmss}.xml`

### DevKit Backup Approach

DevKit should go further than AppMaker by implementing **automatic server-side backup** within the tool, not relying on AI to manually save files.

#### When `get_forms` is called in Detail Mode (with `form_id`):

The tool description instructs AI to use the dedicated `update_form` tool (#11) for modifications:

```
SAFE FORM MODIFICATION WORKFLOW:
1. Call get_forms with form_id to READ the current FormXML
2. Modify the FormXML as needed (follow docs://instructions_for_formxml rules)
3. Call update_form with the modified FormXML
4. update_form auto-handles: backup → validate → update → publish
5. If something breaks: use the backup file path from update_form response to rollback
```

**DO NOT use `execute_webapi` for form updates** — always use `update_form` which provides:
- Auto-backup before overwriting
- XSD validation before writing
- Auto-publish after update
- Rollback instructions in response

#### Future Enhancement (update_form tool -- spec #11):

The `update_form` tool handles all of this automatically:
1. **Auto-retrieve** current FormXML before applying changes
2. **Auto-save** backup to `.devkit/backups/forms/`
3. **Validate** new FormXML against `schema://formxml` XSD before writing
4. **Auto-publish** the entity after update
5. **Return** backup file path in the response for rollback reference

See `11.update_form.md` for full specification.

### Backup File Location

```
{working_directory}/.devkit/backups/forms/
  account_abc123_20260329180000.formxml.bak
  contact_def456_20260329181500.formxml.bak
```

### Rollback Procedure

```
1. Read the backup file
2. PATCH /systemforms({formid}) with body: {"formxml": "<original XML from backup>"}
3. Call publish_customizations for the entity
4. Verify form loads correctly
```

## Implementation Notes

- Query `systemform` table using FetchXML
- Map form type integers to display names in output (Main, QuickCreate, QuickView, etc.)
- FormXML can be very large (10KB+) -- in list mode, only include if `include_formxml=true`
- Filter by `formactivationstate eq 1` by default (only active forms)
- Sort by type then name for consistent ordering
- In detail mode, pretty-print the FormXML with indentation for readability

## Pre-requisite: XSD Schema Resources

When this tool is used to READ FormXML, the AI benefits from understanding the FormXML structure. The MCP Resource (`schema://formxml`) provides the XSD schema from Microsoft's official download:

**Download:** https://download.microsoft.com/download/B/9/7/B97655A4-4E46-4E51-BA0A-C669106D563F/Schemas.zip

Store XSD at: `DynamicsCrm.DevKit.Shared\Resources\xsd\FormXml.xsd`
