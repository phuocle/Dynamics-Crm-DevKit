## Step-by-Step Workflow

### 1. Read the adversarial doc
Read the `.md` file in the `adversarial/` folder (e.g., `03.get_tables.md`). It describes the tool's parameters, edge cases, and expected behaviors.

### 2. Read the tool source code
Open `DynamicsCrm.DevKit.Cli/Mcp/Tools/{ToolName}Tool.cs`. Understand:
- Constructor dependencies (usually `ServiceClient`)
- Input validation paths (return early with error strings)
- Try/catch wrappers around `ServiceClient` calls
- Private/static helper methods
- Return types (`string` vs `CallToolResult`)

### 3. Read existing test file (if any)
Check `DynamicsCrm.DevKit.UnitTests/Cli/Mcp/{ToolName}ToolTests.cs`.

### 4. Write tests using these patterns

#### Pattern A: Null ServiceClient for Validation
```csharp
private static object CreateTool() =>
    Activator.CreateInstance(ToolType, new object?[] { null })!;

[TestMethod]
public void ToolMethod_EmptyInput_ReturnsError()
{
    var tool = CreateTool();
    var result = (string)ExecuteMethod.Invoke(tool, new object?[] { "", ... })!;
    Assert.IsTrue(result.StartsWith("Error:"));
}
```

#### Pattern B: Testing Private/Static Methods via Reflection
```csharp
private static readonly MethodInfo HelperMethod = ToolType
    .GetMethod("MethodName", BindingFlags.NonPublic | BindingFlags.Static)!;

[TestMethod]
public void Helper_WithInput_ReturnsExpected()
{
    var result = HelperMethod.Invoke(null, new object[] { /* args */ });
    Assert.AreEqual(expected, result);
}
```

#### Pattern C: Testing Internal Helper Classes
```csharp
private static readonly Type FormatterType = typeof(McpServerHost).Assembly
    .GetType("DynamicsCrm.DevKit.Cli.Mcp.Tools.Helper.CompactFormatter")!;

private static readonly MethodInfo FormatMethod = FormatterType
    .GetMethod("FormatSomething", BindingFlags.Public | BindingFlags.Static)!;
```

#### Pattern D: Tools returning `CallToolResult`
```csharp
var result = tool.manage_choice(action: "detail", optionset_name: "invalid");
Assert.IsTrue(result.IsError);
var text = ((TextContentBlock)result.Content[0]).Text;
Assert.IsTrue(text.Contains("expected message"));
```

> ⚠️ **Important**: `CallToolResult.IsError` may default to `true` in this SDK version.
> Do NOT assert `Assert.IsFalse(result.IsError)` for `SuccessResult` — verify `Content` instead.

#### Pattern E: Testing ServiceClient-dependent code paths
```csharp
// Pass null ServiceClient → code enters try block → null ref → catch block returns error
var result = (string)ExecuteMethod.Invoke(tool, new object?[] { validInput, ... })!;
Assert.IsTrue(result.StartsWith("Error: Failed to"));
```

### 5. Run tests
```bash
dotnet test DynamicsCrm.DevKit.UnitTests\DynamicsCrm.DevKit.UnitTests.csproj --framework net10.0 --configuration Debug
```

### 6. Run coverage
```bash
dotnet-coverage collect -o "coverage.xml" -f cobertura "dotnet test DynamicsCrm.DevKit.UnitTests\DynamicsCrm.DevKit.UnitTests.csproj --framework net10.0 --configuration Debug"
reportgenerator -reports:"coverage.xml" -targetdir:"Coverage" -reporttypes:"TextSummary"
```

Then check per-tool coverage:
```bash
powershell -ExecutionPolicy Bypass -File Coverage\parse_coverage.ps1
```

Or search the summary:
```powershell
Select-String -Pattern 'ToolName' -Path Coverage\Summary.txt
```

## Coverage Ceiling — ServiceClient Constraint

All MCP tools depend on `ServiceClient` (concrete class, not mockable). The methods that directly call `_serviceClient.RetrieveMultiple()`, `_serviceClient.Execute()`, etc. **cannot be unit tested** without a live Dataverse connection.

### Realistic Coverage Targets

| Return Type | Typical Max Coverage | Explanation |
|-------------|---------------------|-------------|
| `string` | 75-85% | Validation paths + catch blocks covered; internal methods calling ServiceClient uncovered |
| `CallToolResult` | 85-95% | Same + `SuccessResult`/`ErrorResult` helpers can be tested via reflection |

The uncoverable lines are always the **body of private methods** that call:
- `_serviceClient.RetrieveMultiple()`
- `_serviceClient.Execute()`
- `_metadataService.FetchEntityMetadataAsync()`
- Any other ServiceClient/MetadataService method

### How to Maximize Coverage
1. Test ALL input validation branches (empty, null, whitespace, boundary values)
2. Test max_records / parameter capping logic
3. Test private static helper methods via reflection
4. Test helper classes (CompactFormatter, DataverseValueFormatter, FetchXmlPagingHelper) thoroughly
5. Test both normal and get_all paths with null ServiceClient (catch block coverage)
6. Test `SuccessResult`/`ErrorResult` helpers via reflection where applicable
7. Test `ConvertEntities`-style methods that take SDK objects (Entity, EntityMetadata, etc.)

## Important Gotchas

1. **Never use `dotnet build` directly** — use `/build-cli` workflow when needed.
2. **testhost.exe may lock DLLs** — run `taskkill /F /IM testhost.exe` if you see MSB3027 errors.
3. **Reflection BindingFlags**: Internal classes need `Assembly.GetType()`. Private instance methods need `BindingFlags.NonPublic | BindingFlags.Instance`. Private static methods need `BindingFlags.NonPublic | BindingFlags.Static`.
4. **`CallToolResult.IsError`** defaults to `true` in this SDK — don't assert `IsFalse` for success results.
5. **Parameter count**: If a method signature changes (e.g., parameter added/removed), the reflection call will throw `TargetParameterCountException`. Always verify the method signature first.
6. **Coverage counting**: ReportGenerator aggregates inner classes (e.g., `<>c` for lambdas) into the parent class percentage — the Summary.txt number may differ from the XML `line-rate`.

- [ ] Read tool source code
- [ ] Test all input validation branches
- [ ] Test parameter boundary values
- [ ] Test private helpers via reflection
- [ ] Test error wrapping (null ServiceClient → catch block)
- [ ] Test formatter/helper methods used by the tool

- [ ] Run coverage report
- [ ] Coverage at or near ceiling for the tool's architecture
