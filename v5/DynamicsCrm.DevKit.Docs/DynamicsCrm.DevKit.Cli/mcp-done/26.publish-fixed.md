# MCP Tool: publish

## Tool #27 — Solution Management

## Status: IMPLEMENTED

## Purpose

Publish Dataverse customizations to make metadata changes visible to users. After creating/updating entities, attributes, forms, views, option sets, or relationships, changes are NOT visible until published.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entities | string | No | `""` | Comma-separated entity logical names (e.g., `account,contact`). Leave empty to publish ALL. |
| include_global_optionset | bool | No | `false` | Also publish global option sets. Only applies when `entities` is specified. |
| include_sitemap | bool | No | `false` | Also publish the sitemap. Only applies when `entities` is specified. |

## Returns

- Published entity count and names (or "All" for publish all)
- Duration of publish operation
- Status (success/error)

## When to Use

- After ANY metadata change (create/update entity, attribute, form, view, option set, relationship, web resource, sitemap)
- When user reports "I made changes but they're not showing up"
- As the final step in any customization workflow
- After using `execute_webapi` to modify metadata

## Tips

- Publish specific entities when possible (faster than publish all)
- `PublishAll` can take 30+ seconds on large environments
- Publishing already-published changes is harmless (idempotent)
- This is REQUIRED after using `execute_webapi` to modify metadata — other tools like `upsert_form`, `upsert_view` have auto-publish built in

## Example Prompts

> Natural-language prompts that would trigger this tool.

| # | Prompt |
|---|--------|
| 1 | "Publish my changes to the account entity" |
| 2 | "I updated the contact form but changes aren't showing up — publish customizations" |

## Adversarial Review

> Tested against live environment `DEVKITV4` on 2026-04-04. Used `account`, `contact` entities for valid publish; `nonexistent_entity`, `Case`, `lead` for invalid; various malformed inputs for edge cases. 14 live test calls executed.

### Finding 1 — FIXED: Comma-only input silently triggers PublishAll

| Item | Detail |
|------|--------|
| **Severity** | Critical |
| **Status** | **FIXED** — Added `entitiesProvided` flag to distinguish "no parameter" from "parameter with all-empty entries"; returns explicit error when entities parameter is non-empty but yields no valid names |

### Finding 2 — FIXED: Mixed valid+invalid entities fails atomically without partial publish info

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Status** | **FIXED** — Enhanced error message in catch block to include the requested entity list and explicit note that NONE were published due to Dataverse batch rejection |

### Finding 3 — PublishAll can cause MCP connection timeout

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Input** | `entities=""` (empty — triggers PublishAll) |
| **Expected** | Publish completes and returns result |
| **Actual** | `PublishAllXmlRequest` took long enough to cause MCP connection to drop (`Connection closed` error). Server had to be restarted |
| **Root Cause** | `PublishTool.publish()` line 87: `_serviceClient.Execute(new PublishAllXmlRequest())` is synchronous with no timeout control. Large environments can take 30+ seconds, exceeding MCP transport timeout |
| **AI Impact** | AI agent calling publish with empty entities loses MCP connection entirely. The publish may or may not have completed server-side, but the AI has no way to know. Subsequent tool calls fail until MCP is restarted |
| **Status** | **DEFERRED** — Requires architectural change to ServiceClient execution model or MCP transport timeout configuration; cannot be fixed within PublishTool alone |
