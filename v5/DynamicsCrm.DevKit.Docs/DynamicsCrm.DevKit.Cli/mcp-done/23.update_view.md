# MCP Tool: update_view

## Tool #24 — UI Customization

## Status: IMPLEMENTED

## Purpose

Update, create, rename, or undo a Dataverse view (saved query) with automatic backup, FetchXML↔LayoutXML sync validation, and publishing. This is the safe write companion to `get_views` (read).

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| action | string | No | `"update"` | `update` (modify existing), `create` (new view), `rename` (change name), or `undo` (restore from backup) |
| entity_name | string | Yes | — | Entity logical name (e.g., `account`) |
| view_id | string | Cond. | `""` | GUID of the view. Required for `update`, `rename`, `undo`. Ignored for `create`. |
| view_name | string | Cond. | `""` | View name. Required for `create` and `rename`. |
| layoutxml | string | Cond. | `""` | LayoutXML content. Required for `update` and `create`. For `undo`: layout backup file path. |
| fetchxml | string | No | `""` | FetchXML content. Empty = keep existing (update) or auto-generate (create). For `undo`: fetch backup file path. |
| validate | bool | No | `true` | Validate XMLs and check FetchXML↔LayoutXML sync |
| backup | bool | No | `true` | Save current XMLs to local backup before overwriting |
| auto_publish | bool | No | `true` | Publish the entity after changes |

## Returns

- Update status (success/blocked/error)
- Sync validation results (FetchXML ↔ LayoutXML match check)
- Backup file paths (for rollback)
- Publish status

## When to Use

- After reading a view with `get_views` and making modifications
- To add/remove/reorder columns in a view
- To change view filters or sorting
- To create a new public view
- To undo/rollback a previous view change

## Tips

- Critical sync rule: every `<attribute>` in FetchXML MUST have a matching `<cell>` in LayoutXML (and vice versa) — tool validates automatically
- Workflow: `get_views` (read) → modify XMLs → `update_view` (write)
- Read `docs://instructions_for_views` for sync rules and best practices
- Standard column widths: 100 (narrow), 150 (medium), 200 (wide), 300 (extra wide)
- Real data: account has 9 public views including "My Active Accounts" (default), "Active Accounts", "All Accounts"
- Set `auto_publish=false` when batching multiple changes
- Hidden columns: use `ishidden="1"` on a `<cell>` to include a column in the query but hide it from the grid. The column's `<attribute>` MUST still be in FetchXML (sync rule still applies). Common uses: custom icon rendering, JS web resource data, sort/filter support columns. Example: `<cell name="statuscode" width="100" ishidden="1" />`

## Adversarial Review

> Tested against live environment `DEVKITV4` on 2026-04-03. Used account entity views (Active Accounts, My Active Accounts) with 13 live MCP calls.

### Finding 1 — Invalid action silently falls through to "update"

| Item | Detail |
|------|--------|
| **Severity** | Critical |
| **Input** | `action="delete", entity_name="account", view_id="00000000-0000-0000-00aa-000010001002", layoutxml="<grid>...</grid>"` |
| **Expected** | Error: `"delete" is not a valid action. Valid actions: update, create, rename, undo."` |
| **Actual** | Silently treated as `update` — structured result shows `"action":"updated"`. Sync validation happened to block this particular call, but with valid XML it would have updated the view. |
| **Root Cause** | `UpsertViewTool.cs` lines 182-211: `switch (actionName)` uses `default:` branch for the update logic. Any unrecognized action value (e.g., `"delete"`, `"restore"`, `"dlete"` typo) falls through to update. |
| **AI Impact** | An AI agent sending `action="restore"` (common synonym for undo) would silently attempt an update instead of a restore. With valid layoutxml provided, the view would be overwritten. The error message says `"layoutxml required for 'update' action"` which is misleading since the agent asked for "restore". |

### Finding 2 — Doc title says "update_view" but MCP tool name is "upsert_view"

| Item | Detail |
|------|--------|
| **Severity** | Low |
| **Input** | N/A (static analysis) |
| **Expected** | Doc title and H1 should match the actual MCP tool name `upsert_view` |
| **Actual** | Doc file is `23.update_view.md`, H1 says `# MCP Tool: update_view`, but `[McpServerTool(Name = "upsert_view")]` at line 36 |
| **Root Cause** | Tool was likely renamed from `update_view` to `upsert_view` after the doc was written |
| **AI Impact** | Minimal — the doc is for internal reference. But could confuse developers searching for tool docs by MCP name. |

### Finding 3 — Sync validation skips dotted cell names without verifying link-entity alias

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Input** | LayoutXML with `<cell name="nonexistent_alias.emailaddress1" />` |
| **Expected** | Sync validation should warn that `nonexistent_alias` doesn't match any `<link-entity alias="...">` in FetchXML |
| **Actual** | `ValidateSync()` at line 1084: `if (cell.Contains(".")) continue;` — any dotted cell name is silently skipped. An AI could create a cell referencing a non-existent alias and validation would pass. |
| **Root Cause** | `UpsertViewTool.cs` line 1084: blanket skip for all dotted names without checking the alias exists in FetchXML link-entities |
| **AI Impact** | AI agent adds a related entity column with wrong alias → sync check passes → view is updated → column header shows but data is empty for all rows. The view appears broken but no error was raised. |
