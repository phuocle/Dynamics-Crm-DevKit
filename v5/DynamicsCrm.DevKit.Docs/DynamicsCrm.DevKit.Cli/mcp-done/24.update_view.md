# Proposal: update_view MCP Tool

## Priority: 12 (UI Customization Write -- Views are the #2 UI artifact)

## Why This Tool Is Needed

After reading view definitions with `get_views`, AI has NO dedicated tool to update them. The only option is `execute_webapi` with manually constructed PATCH requests. This is especially dangerous for views because:

1. **TWO XML parts must stay in sync** -- FetchXML (query) + LayoutXML (columns). Breaking sync = broken view.
2. **No auto-backup** -- AI must manually save both XMLs
3. **No sync validation** -- AI can add an `<attribute>` in FetchXML but forget the `<cell>` in LayoutXML
4. **No auto-publish** -- Changes invisible without separate publish call

A broken view can **hide all data** from users (broken FetchXML) or **crash the grid** (broken LayoutXML).

### Competitor Analysis (AppMaker)

AppMaker has 4 write tools for views:

| Tool | Parameters | Auto-backup | Sync Validation | Auto-publish |
|------|-----------|-------------|-----------------|--------------|
| `dataverse_view_update_structure` | viewId, layoutXml, fetchXml? | **NO** | **NO** | **YES** |
| `dataverse_view_create` | tableName, viewName, layoutXml, fetchXml? | N/A | **NO** | **YES** |
| `dataverse_view_rename` | viewId, newName | N/A | N/A | **YES** |
| (GetViewDefinition) | viewId | N/A | N/A | N/A |

**AppMaker gaps:** No auto-backup. No FetchXML↔LayoutXML sync validation. No rollback.

**DevKit advantage:** Auto-backup + sync validation + XSD validation + publish in a single safe tool.

## Purpose

Update a Dataverse view's FetchXML and/or LayoutXML with automatic backup, sync validation, and publishing. This is the **safe write companion** to `get_views` (read).

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | - | Entity logical name (e.g., `"account"`). Used for backup naming and publishing. |
| view_id | string | Yes | - | GUID of the view to update. Use `get_views` to find view IDs. |
| layoutxml | string | Yes | - | The new LayoutXML content. Defines column order and widths in the grid. |
| fetchxml | string | No | (empty) | The new FetchXML content. If empty, only LayoutXML is updated (existing FetchXML is kept). |
| validate | bool | No | true | Validate LayoutXML/FetchXML and check sync between them. Blocks update if invalid. |
| backup | bool | No | true | Save current FetchXML + LayoutXML to local backup files before overwriting. |
| auto_publish | bool | No | true | Automatically publish the entity after update. |

## Execution Flow

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. RETRIEVE current view (savedquery by view_id)                │
│    └─ Get current fetchxml + layoutxml + name + entity          │
│    └─ If view not found → error with tip to use get_views       │
├─────────────────────────────────────────────────────────────────┤
│ 2. BACKUP current FetchXML + LayoutXML to local files           │
│    └─ .devkit/backups/views/{entity}_{viewid}_{ts}.fetchxml.bak │
│    └─ .devkit/backups/views/{entity}_{viewid}_{ts}.layoutxml.bak│
├─────────────────────────────────────────────────────────────────┤
│ 3. VALIDATE (if validate=true)                                  │
│    3a. Validate LayoutXML against LayoutXml.xsd                 │
│    3b. Validate FetchXML against Fetch.xsd (if provided)        │
│    3c. SYNC CHECK: every <attribute> in FetchXML must have      │
│        a matching <cell> in LayoutXML (and vice versa)          │
│    └─ If invalid → error with details + DO NOT write            │
├─────────────────────────────────────────────────────────────────┤
│ 4. UPDATE view record in Dataverse                              │
│    └─ Set savedquery.layoutxml = new LayoutXML                  │
│    └─ Set savedquery.fetchxml = new FetchXML (if provided)      │
│    └─ client.Update(view)                                        │
├─────────────────────────────────────────────────────────────────┤
│ 5. PUBLISH entity (if auto_publish=true)                        │
│    └─ PublishXmlRequest for the entity                           │
├─────────────────────────────────────────────────────────────────┤
│ 6. RETURN result with backup file paths for rollback             │
└─────────────────────────────────────────────────────────────────┘
```

## Sync Validation Logic (Critical)

The most important validation: **FetchXML attributes ↔ LayoutXML cells must match**.

```csharp
// Extract attribute names from FetchXML
var fetchDoc = XDocument.Parse(fetchXml);
var fetchAttributes = fetchDoc.Descendants("attribute")
    .Select(a => a.Attribute("name")?.Value)
    .Where(n => n != null)
    .ToHashSet();

// Extract cell names from LayoutXML
var layoutDoc = XDocument.Parse(layoutXml);
var layoutCells = layoutDoc.Descendants("cell")
    .Select(c => c.Attribute("name")?.Value)
    .Where(n => n != null)
    .ToHashSet();

// Check sync
var inFetchNotLayout = fetchAttributes.Except(layoutCells).ToList();
var inLayoutNotFetch = layoutCells.Except(fetchAttributes).ToList();

// Primary key is special -- it's in LayoutXML <row id="entityid"> but may not be in FetchXML attributes
// Filter it out from sync check
```

### Sync Error Examples

```
[Sync Error] FetchXML has attributes not in LayoutXML:
- 'telephone1' is in FetchXML but has no <cell> in LayoutXML → column will be fetched but not displayed

[Sync Error] LayoutXML has cells not in FetchXML:
- 'revenue' is in LayoutXML but has no <attribute> in FetchXML → column header shows but data is empty
```

## Dataverse API

### Retrieve Current View

```csharp
var view = serviceClient.Retrieve("savedquery", viewId,
    new ColumnSet("fetchxml", "layoutxml", "name", "returnedtypecode"));
var currentFetchXml = view.GetAttributeValue<string>("fetchxml");
var currentLayoutXml = view.GetAttributeValue<string>("layoutxml");
```

### Save Backup

```csharp
var backupDir = Path.Combine(workingDirectory, ".devkit", "backups", "views");
Directory.CreateDirectory(backupDir);
var timestamp = DateTime.Now.ToString("yyyyMMddHHmmss");
var fetchBackup = Path.Combine(backupDir, $"{entityName}_{viewId:N}_{timestamp}.fetchxml.bak");
var layoutBackup = Path.Combine(backupDir, $"{entityName}_{viewId:N}_{timestamp}.layoutxml.bak");
File.WriteAllText(fetchBackup, currentFetchXml);
File.WriteAllText(layoutBackup, currentLayoutXml);
```

### Update View

```csharp
var update = new Entity("savedquery", viewId);
update["layoutxml"] = newLayoutXml;
if (!string.IsNullOrEmpty(newFetchXml))
    update["fetchxml"] = newFetchXml;
serviceClient.Update(update);
```

### Publish

```csharp
var publishRequest = new PublishXmlRequest
{
    ParameterXml = $"<importexportxml><entities><entity>{entityName}</entity></entities></importexportxml>"
};
serviceClient.Execute(publishRequest);
```

## Response Format (Compact)

### Success
```
[ViewUpdate] account — Active Accounts (Public)
ViewId: abc-123-def
Status: Updated successfully
Validated: yes (0 errors, sync OK)
Updated: LayoutXML + FetchXML
Backup:
  .devkit/backups/views/account_abc123_20260329180000.fetchxml.bak
  .devkit/backups/views/account_abc123_20260329180000.layoutxml.bak
Published: yes
```

### Sync Validation Failed (view NOT updated)
```
[ViewUpdate] BLOCKED — Sync validation failed
ViewId: abc-123-def
Sync Errors: 2
- 'telephone1' in FetchXML has no matching <cell> in LayoutXML
- 'revenue' in LayoutXML has no matching <attribute> in FetchXML
Backup: not needed (no changes made)
Tip: Ensure every <attribute> in FetchXML has a corresponding <cell> in LayoutXML.
     Refer to docs://instructions_for_views for rules.
```

### Error
```
[Error] View update failed
ViewId: abc-123-def
Message: View with ID 'abc-123-def' not found
Tip: Use get_views with entity_name to find valid view IDs
```

### Rollback Info (always included on success)
```
To rollback this change:
1. Read backup files from .devkit/backups/views/
2. Call update_view with the backup contents as layoutxml + fetchxml
3. Or use execute_webapi: PATCH /savedqueries(abc-123-def) with original fetchxml + layoutxml
```

## Tool Description for AI

```
Update a Dataverse view's LayoutXML and/or FetchXML with automatic backup, sync validation,
and publishing. This is the safe write companion to get_views (read).

PARAMETERS:
- entity_name (required): Entity logical name (e.g., 'account'). Needed for backup and publishing.
- view_id (required): GUID of the view. Use get_views to find view IDs first.
- layoutxml (required): The new LayoutXML content defining column order and widths.
- fetchxml: The new FetchXML content. Leave empty to keep existing FetchXML unchanged.
- validate: Validate XMLs and check FetchXML↔LayoutXML sync (default: true).
- backup: Save current XMLs to local backup before overwriting (default: true).
- auto_publish: Publish the entity after update (default: true).

RETURNS:
- Update status (success/blocked/error)
- Sync validation results
- Backup file paths (for rollback)
- Publish status

WORKFLOW (MUST follow this order):
1. Call get_views with view_id to READ the current FetchXML + LayoutXML
2. Modify the XMLs as needed (follow docs://instructions_for_views rules)
3. Call update_view with the modified XMLs
4. Tool auto-handles: backup → validate → sync-check → update → publish
5. If something breaks: use the backup file paths from the response to rollback

CRITICAL SYNC RULE:
A view has TWO XML parts that MUST stay in sync:
- Every <attribute name="X"> in FetchXML MUST have a <cell name="X"> in LayoutXML
- Every <cell name="X"> in LayoutXML MUST have an <attribute name="X"> in FetchXML
- The tool validates this automatically and BLOCKS the update if out of sync

WHEN TO USE:
- After reading a view with get_views and making modifications
- To add/remove/reorder columns in a view
- To change view filters or sorting
- To adjust column widths

WHEN NOT TO USE:
- To read views (use get_views instead)
- To create a NEW view (future create_view tool)
- To rename a view (use execute_webapi: PATCH /savedqueries({id}) with {"name": "New Name"})

SAFETY:
- Auto-backup saves current FetchXML + LayoutXML before ANY modification
- Sync validation blocks mismatched FetchXML/LayoutXML from being written
- XSD validation blocks structurally invalid XML
- Rollback instructions included in every success response
- If backup=true and backup fails, the update is BLOCKED (fail-safe)

TIPS:
- Always read the current view first with get_views to understand the structure
- Read docs://instructions_for_views for sync rules and best practices
- The <row id="X"> attribute in LayoutXML must be the primary key field (e.g., accountid)
- The <grid jump="X"> attribute is the clickable link column
- Standard column widths: 100 (narrow), 150 (medium), 200 (wide), 300 (extra wide)
- Set auto_publish=false when making multiple changes, then call publish_customizations once
```

## Implementation Notes

- Use `serviceClient.Retrieve("savedquery", ...)` to get current view
- Backup directory: `{workingDirectory}/.devkit/backups/views/`
- **CRITICAL**: If `backup=true` and backup file write fails → ABORT the update (fail-safe)
- Sync validation: parse both XMLs, extract attribute names and cell names, compare sets
- Primary key field (e.g., `accountid`) appears in LayoutXML `<row id="accountid">` but may not be an `<attribute>` in FetchXML — exclude from sync check
- Strip XML declaration from input before writing
- Use `PublishXmlRequest` for entity-specific publishing
- Return both backup file paths in response for rollback reference

## Pre-requisite

- `get_views` tool (#4) must exist to read current view XMLs
- `schema://layoutxml` and `schema://fetchxml` MCP Resources (#2.5) for XSD validation
- `publish_customizations` tool (#1) must exist (or use inline PublishXmlRequest)
- Embedded `LayoutXml.xsd` and `Fetch.xsd` in `DynamicsCrm.DevKit.Shared\Resources\xsd\`

## Dependency Chain

```
get_views (#4) → [AI modifies XMLs] → update_view (#12)
                                            ├── backup (auto)
                                            ├── validate via LayoutXml.xsd + Fetch.xsd (#2.5)
                                            ├── sync check: FetchXML ↔ LayoutXML
                                            └── publish (auto)
```
