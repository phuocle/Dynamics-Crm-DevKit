# MCP Tool: get_forms

## Tool #10 — UI Customization

## Status: IMPLEMENTED

## Purpose

Retrieve form definitions for a Dataverse entity. List mode shows all forms; detail mode returns full FormXML layout definition for a specific form.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | — | Entity logical name (e.g., `account`) |
| form_id | string | No | `""` | GUID of a specific form for full details. Leave empty to list all. |
| form_name | string | No | `""` | Filter forms by name (contains match). Returns detail if exactly 1 match. |
| form_type | int | No | `0` | Filter by type: 2=Main, 5=Mobile, 6=QuickView, 7=QuickCreate |
| include_formxml | bool | No | `false` | In list mode, also include FormXML (default false to save tokens) |

## Returns

- List mode: table of forms with ID, name, type, default status, activation state
- Detail mode: full form metadata + complete FormXML layout definition

## When to Use

- To understand the UI layout of an entity before making customizations
- To find the form ID needed for `build_formxml` or `upsert_form`
- To check which fields are on a form and how they are arranged
- To identify the default main form for an entity

## Tips

- Account entity has 4 main forms: "Account", "Account DevKitV4", "Account for Interactive experience", "Information"
- Use `form_type=2` to get only main forms (most common)
- Use `form_name` for quick lookup by name — returns detail automatically if exactly 1 match
- Set `include_formxml=false` (default) for quick discovery, `true` for detailed analysis

## Adversarial Review

> Tested against live environment `DEVKITV4` on 2026-04-04. Used account entity (10 forms: 4 Main, 1 MainInteractive, 1 QuickCreate, 4 QuickView) and contact entity (6 Main forms). 15 live test calls across 5 categories.

### Finding 1 — FIXED: Negative form_type bypasses filter silently

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Status** | **FIXED** — Added `ValidFormTypes` whitelist; negative and invalid form_type values now return an error listing valid values |

### Finding 2 — FIXED: Invalid form_type values return 0 forms without warning

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Status** | **FIXED** — `ListForms` and `FindFormsByName` validate form_type against `ValidFormTypes` array before querying; invalid values return descriptive error |

### Finding 3 — FIXED: LIKE wildcard injection via form_name

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Status** | **FIXED** — `FindFormsByName` escapes SQL LIKE wildcards (`[`, `%`, `_`) in form_name before building the LIKE pattern |

### Finding 4 — FIXED: Inconsistent Active field format between list and detail mode

| Item | Detail |
|------|--------|
| **Severity** | Low |
| **Status** | **FIXED** — Detail mode `Active` field changed from `yes`/`no` to `Active`/`Inactive` to match list mode |

### Finding 5 — FIXED: Doc file referenced `update_form` instead of `upsert_form`
