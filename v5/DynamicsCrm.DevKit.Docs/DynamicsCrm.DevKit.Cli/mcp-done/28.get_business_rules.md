# MCP Tool: get_business_rules

## Tool #28 — Metadata Discovery

## Status: IMPLEMENTED

## Purpose

List and inspect Dataverse business rules (client-side logic stored as workflow records with category=2) for an entity, including parsed conditions and actions from XAML.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | — | Entity logical name (e.g., 'account', 'msdyn_solutionhistory'). |
| rule_id | string | No | `""` | GUID of a specific business rule for full detail (conditions + actions). Leave empty to list all. |
| status | string | No | `""` | Filter by `"active"` (activated rules) or `"draft"` (deactivated). Leave empty for all. |
| max_records | int | No | 50 | Maximum rules to return (max: 200). |

## Returns

- **List mode** (no rule_id): TSV table of rules with ruleId, name, scope, status, modifiedOn
- **Detail mode** (rule_id provided): Full rule info with scope, status, created/modified metadata, plus parsed conditions (IF field operator value) and actions (SetVisibility, SetRequired, SetValue, ShowError, LockField, UnlockField, SetDefaultValue)

## When to Use

- Debugging form behavior where fields hide/show unexpectedly
- Understanding existing client-side logic before adding JavaScript to a form
- Auditing what business rules run on an entity and their scope (Organization vs Form-specific)
- Checking for conflicts between business rules and custom form scripts
- Investigating why a field is suddenly required or locked on a form

## Tips

- Business rules run client-side and execute BEFORE JavaScript form events
- Scope "Organization" means the rule runs on ALL forms for that entity
- Call `get_entity_metadata` first to understand available fields before inspecting rule conditions
- Use `get_forms` to see which forms a rule may apply to
- The tool parses XAML (not clientdata) using regex for reliable condition/action extraction
- Active rules have `statecode=1`, draft rules have `statecode=0`

## Adversarial Review

> Tested against live environment `DEVKITV4` on 2026-04-02. Entity `msdyn_solutionhistory` (3 active business rules) used as primary test subject.

### Finding 1 — Invalid `status` value silently ignored (returns unfiltered results)

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Input** | `entity_name="msdyn_solutionhistory"`, `status="INVALID_STATUS"` |
| **Expected** | Error message like `"Error: Invalid status value 'INVALID_STATUS'. Use 'active' or 'draft'."` |
| **Actual** | Returns all 3 rules with no error — behaves as if `status=""` |
| **Root Cause** | `BuildListFetchXml` (line 197-226): the status string is lowercased and compared to `"active"` / `"draft"`, but if it matches neither, `filterStatus` stays empty and no filter is applied. No validation or warning. |
| **AI Impact** | An AI agent that passes `status="activated"` (matching the display value shown in results) or `status="on"` will silently get unfiltered results and believe it received only active/draft rules. This leads to **incorrect downstream reasoning**. |

### Finding 2 — Tool description says "parsed from clientdata" but code parses `xaml`

| Item | Detail |
|------|--------|
| **Severity** | Low (documentation mismatch) |
| **Input** | N/A — static code analysis |
| **Expected** | Tool `[Description]` attribute and actual behavior should match |
| **Actual** | Line 38 in `[Description]`: `"Detail mode: Full rule info with conditions and actions parsed from clientdata"`. Actual code (line 137): retrieves `"xaml"` column. Line 182: calls `ParseXaml(sb, xaml)`. |
| **Root Cause** | The `[Description]` annotation was not updated when the implementation was changed from `clientdata` to `xaml` parsing. |
| **AI Impact** | An AI reading the tool description may tell the user _"I parsed the clientdata field"_ when in reality the tool parsed `xaml`. If the AI later needs to debug a parsing issue, it would look at the wrong field. The doc file (line 39) correctly states "parses XAML (not clientdata)" but the tool's own embedded description contradicts this. |

### Finding 3 — Plural grammar: `(1 rules)` instead of `(1 rule)`

| Item | Detail |
|------|--------|
| **Severity** | Low (cosmetic) |
| **Input** | `entity_name="msdyn_solutionhistory"`, `max_records=1` |
| **Expected** | `[BusinessRules] msdyn_solutionhistory (1 rule)` |
| **Actual** | `[BusinessRules] msdyn_solutionhistory (1 rules)` |
| **Root Cause** | Line 108: `sb.AppendLine($"[BusinessRules] {entityName} ({result.Entities.Count} rules)")` — hardcoded plural. |
| **AI Impact** | Minimal. But for tools designed to be consumed by AI, grammatical inconsistency can reduce parsing confidence. Other DevKit tools (e.g., `get_forms`, `get_views`) handle singular/plural correctly. |
