# MCP Tool: update_form

## Tool #22 — UI Customization

## Status: IMPLEMENTED

## Purpose

Update, rename, or undo a Dataverse form with automatic backup, XSD schema validation, and publishing. This is the safe write companion to `get_forms` (read).

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| action | string | No | `"update"` | `update` (modify FormXML), `rename` (change name), or `undo` (restore from backup) |
| entity_name | string | Yes | — | Entity logical name (e.g., `account`). Needed for backup naming and publishing. |
| form_id | string | Yes | — | GUID of the form. Use `get_forms` to find form IDs. |
| form_name | string | Cond. | `""` | New display name for the form. Required for `rename`. |
| formxml | string | Cond. | `""` | For `update`: new FormXML content. For `undo`: backup file path. |
| validate | bool | No | `true` | Validate FormXML against XSD before writing |
| backup | bool | No | `true` | Save current FormXML to local backup before overwriting |
| auto_publish | bool | No | `true` | Publish the entity after changes |

## Returns

- Update status (success/blocked/error)
- Validation results (if validate=true)
- Backup file path (for rollback)
- Publish status

## When to Use

- After reading a form with `get_forms` and making modifications to the FormXML
- To add/remove/rearrange tabs, sections, or fields on a form
- To rename a form's display name
- To undo/rollback a previous form change using a backup file

## Tips

- Workflow: `get_forms` (read) → modify XML → `update_form` (write) — tool auto-handles backup → validate → update → publish
- Read `schema://formxml` for the XSD schema reference and `docs://instructions_for_formxml` for best practices
- If backup=true and backup fails, update is BLOCKED (fail-safe)
- Set `auto_publish=false` when batching multiple changes, then call `publish` once
- Real data: account has 4 main forms including "Account" (default), "DevKitV4" (customized with v4_* fields)

## Adversarial Review

> Tested against live environment `DEVKITV4` on 2026-04-05. Used account form `Account DevKitV4` (38c60f9f-e1db-f011-8406-0022480b95a5, unmanaged) and contact forms for cross-entity tests.

### Finding 1 — FIXED: Invalid action silently treated as "update"

| Item | Detail |
|------|--------|
| **Severity** | Critical |
| **Status** | **FIXED** — Replaced `default:` switch case with explicit `case "update":` and a `default:` that returns an error for unrecognized actions. |

### Finding 2 — FIXED: Rename action crashes with OptionSetValue cast exception

| Item | Detail |
|------|--------|
| **Severity** | Critical |
| **Status** | **FIXED** — Changed `GetAttributeValue<int?>("type")` to `GetAttributeValue<OptionSetValue>("type")?.Value` to correctly read the OptionSet field. |

### Finding 3 — FIXED: Entity name not validated against actual form entity

| Item | Detail |
|------|--------|
| **Severity** | Critical |
| **Status** | **FIXED** — Added entity mismatch validation in all three action paths (update, rename, undo) that compares user-provided `entity_name` against the form's `objecttypecode` and returns a clear error on mismatch. |

### Finding 4 — FIXED: Rename swallows publish failure silently

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Status** | **FIXED** — Replaced empty `catch { }` with `catch (Exception ex)` that captures the error message. Added `PublishError:` and retry tip to the text output, consistent with the update path. |
