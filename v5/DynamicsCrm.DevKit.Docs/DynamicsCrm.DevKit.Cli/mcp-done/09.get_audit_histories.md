## Why This Tool Is Needed

In enterprise D365 projects, **"who changed what and when"** is a daily question. Audit logs are essential for:

1. **Compliance** — GDPR, SOX, HIPAA require audit trails
2. **Debugging** — "This field used to be X, who changed it?"
3. **Data disputes** — "Sales says the deal was $1M, but it's showing $500K"
4. **Integration troubleshooting** — "Something is overwriting our data every night"

Currently, AI has **no way** to query audit history. Users must navigate the CRM UI → Record → Related → Audit History, which is slow and not automatable.

## Dataverse API

### Retrieve Audit History

```csharp
var request = new RetrieveRecordChangeHistoryRequest
{
    Target = new EntityReference(entityName, recordId),
    PagingInfo = new PagingInfo
    {
        PageNumber = 1,
        Count = maxRecords
    }
};

var response = (RetrieveRecordChangeHistoryResponse)serviceClient.Execute(request);
var auditDetails = response.AuditDetailCollection;
```

### Process Audit Details

```csharp
foreach (var auditDetail in auditDetails.AuditDetails)
{
```

## Tool Description for AI

```
Retrieve audit history for a specific Dataverse record.
Shows who changed what fields, when, with old and new values.

PARAMETERS:
- entity_name (required): Entity logical name (e.g., 'account').
- record_id (required): GUID of the record.
- minutes_ago: Return entries from last N minutes (default: 1440 = 24h, max: 43200 = 30 days).
- user_id: Filter by user email or GUID.
- operation: Filter by 'Create', 'Update', or 'Delete'.
- attribute_name: Show changes only for a specific field.
- max_records: Maximum entries to return (default: 50, max: 500).

RETURNS:
- Table of audit entries: timestamp, user, action, field, old value, new value

WHEN TO USE:
- When a user asks "who changed this field?" or "when was this record modified?"
- To debug unexpected data changes (e.g., integration overwriting values)
- For compliance auditing (GDPR, SOX data change trails)
- To investigate data disputes ("the deal was supposed to be $1M")
- After a data issue to trace the root cause

TIPS:
- Audit must be enabled at organization level AND entity level to work
- Not all field changes are audited — only fields with auditing enabled
- Create actions show all initial field values
- Use user_id filter to find changes made by a specific user or integration account
- Use attribute_name to focus on a specific field's change history
```

## Implementation Notes

- Use SDK `RetrieveRecordChangeHistoryRequest` (not WebAPI)
- Handle `AttributeAuditDetail` for field-level changes
- Format old/new values using `DataverseValueFormatter` (handle lookups, optionsets, money, dates)
- Filter by `minutes_ago` client-side on `createdon` attribute of audit records
- Filter by `user_id` client-side on `userid` attribute
- Handle case where auditing is disabled globally or per-entity
- Display user-friendly names (resolve user GUIDs to display names)

## Pre-requisite

- Audit must be enabled in the Dataverse environment (System Settings → Auditing)
- Entity-level auditing must be enabled for the target entity

## Gap Analysis Summary

### Severity Classification

| Severity | Count | Issues |
|----------|-------|--------|
| **Critical** (tool cannot do, no workaround) | 4 | #11 entity-wide audit, #12 email filter + entity-wide, #13 deleted records, #16 cross-entity |
| **Medium** (tool description bug) | 1 | #17 operation filter only documents 3 of 9 supported actions |
| **Low** (edge cases, AI can partially work around) | 5 | #14 aggregation, #15 point-in-time, #18 access logs, #19 date range, #20 N:N relationships |

### Root Cause: Single-Record Scope

The fundamental limitation is that `RetrieveRecordChangeHistoryRequest` requires a **specific EntityReference** (entity + GUID). This means:

- **Entity-wide queries** ("all changes to any account") are impossible
- **Cross-entity queries** ("all changes by user X") are impossible
- **Deleted record queries** are impossible (GUID no longer resolves)

To cover these cases, a separate tool (e.g., `query_audit_log`) would be needed that queries the `audit` entity directly via FetchXML:

```xml
<fetch>
  <entity name='audit'>
    <attribute name='createdon'/>
    <attribute name='userid'/>
    <attribute name='objectid'/>
    <attribute name='action'/>
    <attribute name='attributemask'/>
    <filter>
      <condition attribute='objecttypecode' operator='eq' value='1'/> <!-- account -->
      <condition attribute='createdon' operator='last-x-days' value='7'/>
    </filter>
  </entity>
</fetch>
```

### Recommended Fix: Operation Description

The `operation` parameter description should be updated from:

```
"Values: 'Create', 'Update', 'Delete'."
```

To:

```
"Values: 'Create', 'Update', 'Delete', 'Activate', 'Deactivate', 'Assign', 'Merge', 'Cascade', 'SetState'."
```

This is a **zero-code change** — only the `[Description()]` string needs updating in [GetAuditHistoryTool.cs:76-78](DynamicsCrm.DevKit.Cli/Mcp/Tools/GetAuditHistoryTool.cs#L76-L78).
