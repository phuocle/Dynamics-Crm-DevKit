# Proposal: get_workflows MCP Tool

## Priority: 7 (Business Logic Discovery -- Understand automation on an entity)

## Scope

> **Classic Workflows ONLY** (category=0 in the `workflow` table).
> This tool does NOT cover: Business Rules (→ `get_rules`), Actions, BPFs, Modern Flows, Desktop Flows, Dialogs.
> Each of those has (or will have) its own dedicated tool.

## Why This Tool Is Needed

Classic workflows (background & real-time) are a core automation mechanism in Dataverse. AI agents need to:

- Discover which workflows exist on an entity and what triggers them
- Answer field-level questions: "Does field X on entity Y have any workflow triggered?"
- Detect potential conflicts before registering a new plugin or workflow
- Audit execution behavior: sync vs async, pipeline stage, scope, run-as context

## Purpose

List classic workflows (background and real-time) registered for an entity. Returns trigger configuration AND supplementary execution fields so AI can fully reason about workflow behavior.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `entity_name` | string | No | (empty) | Filter by entity logical name (e.g., `"account"`). Leave empty for all entities. |
| `mode` | string | No | (empty) | Filter by execution mode: `"background"` (0) or `"realtime"` (1). Leave empty for both. |
| `active_only` | bool | No | true | Only return activated workflows. Default: true. |
| `trigger_field` | string | No | (empty) | Filter workflows whose `triggeronupdateattributelist` contains this attribute (e.g., `"revenue"`). Uses `like %value%`. |
| `name_filter` | string | No | (empty) | Filter by workflow name (contains match). |
| `max_records` | int | No | 50 | Maximum records. Default: 50, max: 250. |

## Dataverse Table

**Entity:** `workflow` | **Entity Set:** `/workflows` | **Filter:** `category eq 0` (Workflow), `type eq 1` (Definition)

### Key Columns (Returned)

#### Identity

| Column | Type | Description |
|--------|------|-------------|
| `workflowid` | Guid | Primary key |
| `name` | String | Workflow display name |
| `primaryentity` | EntityName | Entity logical name (e.g., `account`, `contact`) |
| `description` | String | Workflow description |

#### Trigger Configuration

| Column | Type | Description |
|--------|------|-------------|
| `triggeroncreate` | Boolean | Fires on record Create |
| `triggerondelete` | Boolean | Fires on record Delete |
| `triggeronupdateattributelist` | String (comma-separated) | Attribute logical names that trigger on Update. Empty = no update trigger. Contains `statecode`/`statuscode` = status change trigger. Contains `ownerid` = assign trigger. |

> **How "Status Change" and "Assign" work under the hood:**
> - Status change = `triggeronupdateattributelist` includes `statecode` and/or `statuscode`
> - Record assigned = `triggeronupdateattributelist` includes `ownerid`
> - There is NO separate "trigger on status change" or "trigger on assign" boolean — they are all Update triggers filtered by attributes.

#### Pipeline Stage (Real-time workflows only)

| Column | Type | Options | Description |
|--------|------|---------|-------------|
| `createstage` | Picklist | 20=Pre-operation, 40=Post-operation | Pipeline stage on Create trigger |
| `updatestage` | Picklist | 20=Pre-operation, 40=Post-operation | Pipeline stage on Update trigger |
| `deletestage` | Picklist | 20=Pre-operation, 40=Post-operation | Pipeline stage on Delete trigger |

> Background workflows always execute Post-operation (async). Only Real-time workflows can choose Pre-operation (can cancel/rollback) or Post-operation.

#### Execution Behavior

| Column | Type | Options | Description |
|--------|------|---------|-------------|
| `mode` | Picklist | 0=Background, 1=Realtime | Background=async (queued), Realtime=sync (in pipeline) |
| `scope` | Picklist | 1=User, 2=BusinessUnit, 3=Parent:ChildBU, 4=Organization | Which records the workflow applies to |
| `runas` | Picklist | 0=Owner, 1=CallingUser | Security context for execution |
| `rank` | Integer | - | Execution order. Lower=first. Matters when multiple real-time workflows fire on same event. |
| `ondemand` | Boolean | - | Can be run manually by users |
| `subprocess` | Boolean | - | Can be called as a child workflow from another workflow |
| `istransacted` | Boolean | - | Runs in a single DB transaction (rollback on failure) |
| `asyncautodelete` | Boolean | - | Auto-delete system job on completion (background only) |

#### State & Audit

| Column | Type | Options | Description |
|--------|------|---------|-------------|
| `statecode` | State | 0=Draft, 1=Activated | Lifecycle state |
| `ismanaged` | Boolean | - | Part of a managed solution |
| `ownerid` | Owner | - | Workflow owner (user or team) |
| `modifiedby` | Lookup | - | Last modifier |
| `modifiedon` | DateTime | - | Last modified date |

### FetchXML Query Pattern

```xml
<fetch>
  <entity name="workflow">
    <!-- Identity -->
    <attribute name="workflowid" />
    <attribute name="name" />
    <attribute name="primaryentity" />
    <attribute name="description" />
    <!-- Triggers -->
    <attribute name="triggeroncreate" />
    <attribute name="triggerondelete" />
    <attribute name="triggeronupdateattributelist" />
    <!-- Pipeline Stage -->
    <attribute name="createstage" />
    <attribute name="updatestage" />
    <attribute name="deletestage" />
    <!-- Execution Behavior -->
    <attribute name="mode" />
    <attribute name="scope" />
    <attribute name="runas" />
    <attribute name="rank" />
    <attribute name="ondemand" />
    <attribute name="subprocess" />
    <attribute name="istransacted" />
    <attribute name="asyncautodelete" />
    <!-- State & Audit -->
    <attribute name="statecode" />
    <attribute name="ismanaged" />
    <attribute name="ownerid" />
    <attribute name="modifiedby" />
    <attribute name="modifiedon" />
    <filter type="and">
      <condition attribute="category" operator="eq" value="0" />
      <!-- Classic Workflow only -->
      <condition attribute="type" operator="eq" value="1" />
      <!-- Definition only (exclude Activation copies and Templates) -->
      <!-- Add: entity_name filter if provided -->
      <!-- Add: mode filter if provided -->
      <!-- Add: statecode=1 if active_only=true -->
      <!-- Add: triggeronupdateattributelist like '%field%' if trigger_field provided -->
      <!-- Add: name like '%value%' if name_filter provided -->
    </filter>
    <order attribute="primaryentity" />
    <order attribute="name" />
  </entity>
</fetch>
```

## Tool Description for AI

```
List classic workflows (background and real-time) for a Dataverse entity.
Returns trigger configuration and execution behavior fields.

SCOPE: Classic workflows only (category=0). Does NOT include business rules,
actions, BPFs, or cloud flows — use dedicated tools for those.

PARAMETERS:
- entity_name: Filter by entity (e.g., 'account'). Leave empty for all.
- mode: Filter by execution mode: 'background' or 'realtime'. Leave empty for both.
- active_only: Only return activated workflows (default: true).
- trigger_field: Filter workflows that trigger on a specific field (e.g., 'revenue').
  Searches triggeronupdateattributelist using contains match.
- name_filter: Filter by workflow name (contains match).
- max_records: Maximum records (default: 50, max: 250).

RETURNS:
- Table: name, mode, triggers (Create/Delete/Update), update fields,
  pipeline stage, scope, runAs, rank, ondemand, subprocess, status, modified
- Summary: count by mode, trigger type

KEY FIELDS EXPLAINED:
- triggeronupdateattributelist: comma-separated field names that trigger on Update.
  This is the most important field for field-level questions.
  'statecode'/'statuscode' in this list = triggered by status change.
  'ownerid' in this list = triggered by record assignment.
- mode: 0=Background (async, queued), 1=Realtime (sync, in pipeline)
- createstage/updatestage/deletestage: pipeline stage (20=Pre, 40=Post).
  Only meaningful for Realtime workflows. Pre-operation can cancel the operation.
- scope: 1=User, 2=BU, 3=Parent:ChildBU, 4=Org
- runas: 0=Owner (workflow owner's privileges), 1=CallingUser (triggering user's privileges)
- rank: execution order when multiple real-time workflows fire on same event (lower=first)

WHEN TO USE:
- "Does field X on entity Y have any workflow triggered?"
  → Use trigger_field='X' + entity_name='Y'
- "What workflows trigger when a record status changes?"
  → Use trigger_field='statecode' (or 'statuscode')
- "What workflows trigger when a record is assigned?"
  → Use trigger_field='ownerid'
- "What real-time (synchronous) workflows exist on this entity?"
  → Use mode='realtime' + entity_name
- "What automation runs before a record is created?"
  → Use mode='realtime', check createstage=20 (Pre-operation)
- "What is the full picture of automation on this entity?"
  → Combine with get_rules (business rules) and get_plugin_registrations (plugins)
- "Are there conflicting workflows?" → Check rank, mode, and overlapping trigger fields

TIPS:
- Always filter type=1 (Definition) to avoid duplicate Activation records
- Background workflows always run Post-operation (async) — stage fields are irrelevant
- Realtime workflows with Pre-operation stage can cancel/rollback the operation
- A non-empty triggeronupdateattributelist implies the workflow triggers on Update
- If triggeronupdateattributelist is empty/null AND triggeroncreate=false AND
  triggerondelete=false, the workflow is likely on-demand only (check ondemand=true)
```

## Implementation Notes

- **MUST filter** `category eq 0` (classic Workflow) AND `type eq 1` (Definition only)
- Build `triggers` display column from `triggeroncreate` + `triggeronupdateattributelist` + `triggerondelete` + `ondemand`
- Map picklist integers to display names (mode, scope, runas, stages)
- `triggeronupdateattributelist` is the key field for field-level filtering — use FetchXML `like` operator with `%field%`
- When `trigger_field` is provided, also check `triggeroncreate` and `triggerondelete` are irrelevant — only `triggeronupdateattributelist` matters for field-level filtering
- Real-time workflows with `mode=1` behave like synchronous plugins — mention this in output when relevant
- `rank` determines execution order among multiple real-time workflows on the same event
- `subprocess=true` means it can be called from another workflow (not directly triggered by events)
- `ondemand=true` means users can run it manually from the command bar
