# MCP Tool: get_rules

## Tool #28 — Metadata Discovery

## Status: IMPLEMENTED

## Purpose

List and inspect Dataverse business rules (client-side logic stored as workflow records with category=2) for an entity, including parsed conditions and actions from XAML.

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| entity_name | string | Yes | — | Entity logical name (e.g., 'account', 'msdyn_solutionhistory'). |
| rule_id | string | No | `""` | GUID of a specific business rule for full detail (conditions + actions). Leave empty to list all. |
| status | string | No | `""` | Filter by `"active"` (activated rules) or `"draft"` (deactivated). Leave empty for all. |
| max_records | int | No | 50 | Maximum rules to return (max: 200). |

## Returns

- **List mode** (no rule_id): TSV table of rules with ruleId, name, scope, status, modifiedOn
- **Detail mode** (rule_id provided): Full rule info with scope, status, created/modified metadata, plus parsed conditions (IF field operator value) and actions (SetVisibility, SetRequired, SetValue, ShowError, LockField, UnlockField, SetDefaultValue)

## When to Use

- Debugging form behavior where fields hide/show unexpectedly
- Understanding existing client-side logic before adding JavaScript to a form
- Auditing what business rules run on an entity and their scope (Organization vs Form-specific)
- Checking for conflicts between business rules and custom form scripts
- Investigating why a field is suddenly required or locked on a form

## Tips

- Business rules run client-side and execute BEFORE JavaScript form events
- Scope "Organization" means the rule runs on ALL forms for that entity
- Call `get_metadata_entities` first to understand available fields before inspecting rule conditions
- Use `get_forms` to see which forms a rule may apply to
- The tool parses XAML (not clientdata) using regex for reliable condition/action extraction
- Active rules have `statecode=1`, draft rules have `statecode=0`
