# Conventions chung khi viết description cho MCP tools

File này gom các quy ước thống nhất cho 36 tool. Mục tiêu: AI khác đọc 1 lần là apply được cho mọi tool, tránh lặp text trong từng tool description.

---

## 1. WHEN TO USE — phải có và phải tách block

Mỗi tool MUST giữ 1 block `WHEN TO USE` ngắn (1–3 bullet) **tách riêng** khỏi phần mô tả chức năng. Lý do:

- AI hay đọc description theo trình tự "what → when → how"; gom "Use to..." inline khiến phần "when" bị mờ và AI lựa tool sai khi có 2 tool gần nhau.
- Hai tool chức năng giống nhưng phạm vi khác (ví dụ `get_workflows` vs `get_flows`, `manage_command` vs `manage_ribbon`) cần WHEN TO USE rõ để route.
- Khi optimize không được gộp WHEN TO USE vào câu mô tả chính.

**Format chuẩn:**

```text
WHEN TO USE:
- <tình huống 1>
- <tình huống 2>
```

Chỉ giữ bullet thực sự bổ sung thông tin mới so với câu mô tả; bullet đã suy ra được từ ACTIONS/MODES thì bỏ.

## 2. Convention cho tool tên kết thúc bằng `s` (plural)

Tất cả tool tên kết thúc bằng `s` (plural noun) đều theo pattern **list/detail by ID** với 1 quy ước thống nhất:

| Param ID | Empty | Provided |
|---|---|---|
| `<entity>_id` (e.g. `record_id`, `bpf_id`, `flow_id`, `workflow_id`, `rule_id`, `api_name`, `assembly_name`…) | **List mode** — return summary table với filters | **Detail mode** — return full object |

**13 tool theo convention này:**

`get_tables`, `get_messages`, `get_solution_components`, `get_plugin_trace_logs`, `get_system_jobs`, `get_business_rules`, `get_workflows`, `get_custom_apis`, `get_flows`, `get_business_process_flows`, `get_plugins`, `search_records` (action-based variant), `create_records` (bulk variant — exception)

> **Note exception:** `create_records` là bulk-create, không phải list/detail. `search_records` dùng `action` thay vì id-presence.

**Cách viết trong description (ngắn, không lặp):**

```text
<id_param> empty = list (filtered). Set = detail.
```

Không cần liệt kê dài "MODES" 2-3 dòng nữa nếu pattern đã chuẩn. Chỉ liệt kê khi có ≥3 modes hoặc behavior khác (như `get_flows` có 3 modes vì action='runs').

## 3. Fuzzy lookup disambiguation — TOOL DỪNG, HỎI USER

Nhiều tool nhận tên (display name / friendly name) thay vì GUID và resolve bằng fuzzy `contains` match. Quy ước an toàn:

| # matches | Hành vi tool | Hành vi AI |
|---:|---|---|
| **0** | Trả error: "no match" | Báo lại user, gợi ý dùng `list` action để xem tên hợp lệ |
| **1** | Auto-resolve → tiếp tục (hoặc auto-detail nếu là `*_name` filter trong list mode) | OK, dùng kết quả |
| **2+** | **Trả disambiguation list, KHÔNG auto-pick** | **DỪNG, hiển thị list, hỏi user chọn chính xác (uniqueName/GUID)** |

**Critical rule cho AI:** khi tool trả về 2+ matches, AI **không được tự đoán** "match đầu tiên có vẻ đúng". Phải:

1. Hiển thị danh sách candidates cho user
2. Hỏi user chọn chính xác (uniqueName, GUID, hoặc displayName cụ thể hơn)
3. Re-call tool với giá trị đã được user xác nhận

**Tools áp dụng fuzzy disambiguation:**

| Tool | Param | Match field |
|---|---|---|
| `get_solution_components` | `solution_name` | uniqueName + displayName (contains) |
| `manage_form` | `form_name` | name (contains, 1 match → auto-detail) |
| `manage_view` | `view_name` | name (contains, 1 match → auto-detail) |
| `manage_role` | `role_name` | name (contains) |
| `build_sitemap_xml` | `app` | display name + GUID (fuzzy) |
| `manage_sitemap` | `app` | display name + GUID (fuzzy) |
| `get_workflows` | `name_filter` | name (contains, 1 match → auto-detail) |
| `get_flows` | `name_filter` / `owner_filter` | name / owner (contains) |
| `get_business_process_flows` | `bpf_name` | name (contains, 1 match → auto-detail) |
| `manage_command` | `label` | label resolution + entity_name + location |
| `get_messages` | `message_name` | exact-ish but case-insensitive |

**Cách viết trong description (ngắn):**

```text
<param>: fuzzy contains match. 0/2+ matches → tool returns disambiguation list and stops; AI must ask user to disambiguate. 1 match → auto-resolve.
```

Hoặc shorthand cuối description:

```text
Fuzzy on <param>: 0/multi → disambiguate (AI must ask user). 1 → auto.
```

## 4. Áp dụng convention vào file optimized

Khi review/update bản After-optimize của từng tool, đảm bảo:

- [ ] Có block `WHEN TO USE` riêng (ngắn, không gộp inline)
- [ ] Nếu tên tool kết thúc bằng `s` và là list/detail-by-id pattern → dùng câu shorthand `<id_param> empty = list. Set = detail.` thay vì khối MODES dài
- [ ] Nếu tool có fuzzy-resolved name param → thêm 1 dòng ở cuối description: `Fuzzy on <param>: 0/multi → disambiguate (AI must ask user). 1 → auto.`
- [ ] Không gộp WHEN TO USE vào câu mô tả chính (bằng "Use to..." inline)

---

## 5. Định nghĩa shorthand đã dùng (giữ nhất quán)

| Shorthand | Ý nghĩa |
|---|---|
| `[create-only]` | param chỉ áp dụng khi action=create, immutable sau đó |
| `[update-only]` | param chỉ áp dụng khi action=update |
| `[update: omit=keep]` | trên action=update, omit param = giữ giá trị hiện tại |
| `BTN_FN` (build_ribbon_xml) | `library, function, enable_library, enable_function` |
| `BTN_OPT` (build_ribbon_xml) | `modern_image, tooltip_title, tooltip_description, sequence` |

---

## 6. Phần "Tổng kết tiết kiệm token" — cần audit lại sau khi áp 3 quy ước trên

Khi restore WHEN TO USE và thêm fuzzy/`_s` convention, một vài tool sẽ tăng nhẹ vài chục tokens. Cập nhật con số tiết kiệm trong từng file để phản ánh chính xác.
