01. Chưa cần port new-project sang MCP ngay

Với AI đang làm việc trong repository và có quyền chạy process, guide gọi devkit new-project là đủ để sử dụng chức năng tạo project hiện tại. Chất lượng project sinh ra đến từ Shared engine và template payload; đổi cách gọi sang MCP không tự cải thiện nội dung sinh ra.

Ưu tiên hiện tại

Chuẩn hóa hướng dẫn: discovery → chọn solution → kiểm tra phụ thuộc → chạy CLI không tương tác → đọc exit code và file diff. Giữ một nguồn hướng dẫn dùng chung cho các AI client.

Giữ khả năng mở rộng

Nếu có client chỉ dùng MCP và truy cập được workspace đích, bổ sung adapter mỏng gọi ScaffoldingEngine. Không cần sao chép handler hay chuyển toàn bộ CLI thành MCP.

Điều kiện của kết luận: AI có terminal, máy đó cài devkit, có filesystem access tới solution và người dùng đã yêu cầu tạo project. Nếu thiếu terminal, hướng dẫn bằng văn bản không tự cấp khả năng thực thi; lúc ấy cần tích hợp khác, có thể là MCP.

Đây là đề xuất điều chỉnh thứ tự ưu tiên, chưa phải thay đổi roadmap đã được duyệt. Báo cáo không triển khai tool mới, không sửa API CLI, không sửa các file kế hoạch P.* / I.*.

04. Kế hoạch trong Vsix2CliAndMcp có bắt buộc làm MCP ngay?

Bản tổng quan chọn CLI trước, MCP sau; 0.md §6 để MCP phase 2 sau khi P.* và I.* hoàn tất. I.18 §8 cũng đặt mốc mở phase MCP ở cuối track item. Đây là kế hoạch có điều kiện, không phải yêu cầu rằng AI chỉ được tạo project thông qua MCP.

Giá trị của hướng core chung vẫn đúng: payload có một nguồn, handler nằm Shared, adapter thu thập input. Có thể sử dụng CLI lâu dài và vẫn giữ kiến trúc đó. Việc chưa làm MCP không làm phí công tách core.

Câu “MCP gần như free” trong tổng quan cần hiểu hẹp: phần render có thể tái sử dụng, nhưng host lifecycle, quyền ghi workspace, contract parameters, concurrency, partial failure và kiểm thử adapter vẫn cần làm. Map tham số vài dòng chưa tạo thành một chức năng MCP hoàn chỉnh.

06. “Chỉ guide AI” cần cụ thể như thế nào?

Không nên chỉ ghi một câu “hãy gọi new-project”. Guide cần mô tả điều kiện chạy, discovery, phụ thuộc và cách xử lý lỗi. Nên đặt recipe dùng chung dưới DynamicsCrm.DevKit.AI/workflows/, dẫn tới reference Cli/new.md; bridge của từng client chỉ trỏ tới recipe, tránh nhân bản quy tắc.

  1. Khám phá binary: chạy version, list và help. Chỉ chọn project type Ready=yes; dừng với type chưa sẵn sàng.
  2. Chốt workspace: xác định solution thật và output parent. Có nhiều solution thì cần biết đúng file; luôn truyền đường dẫn tường minh. Nếu chưa có solution, tạo solution là bước riêng được người dùng yêu cầu; new-project không tự tạo file solution bị thiếu.
  3. Kiểm tra phụ thuộc: Server cần Shared. Test cần Shared, ProxyTypes, SharedTest. Tạo từng project theo thứ tự; không chạy đồng thời các lệnh cùng sửa một solution.
  4. Kiểm tra thư mục đích: project cùng tên đã tồn tại thì dừng và đọc trạng thái. Không tự xóa source hay đổi tên ngẫu nhiên để lệnh chạy được.
  5. Gọi không tương tác: thêm --plain, truyền đủ type/name/solution/out, quote từng path. Không truyền secret vì project scaffolding không cần login org.
  6. Đọc kết quả: thu stdout/stderr và exit code ngay sau lệnh. Thành công thì xem file/project/solution diff. Thất bại thì sửa đúng nguyên nhân, kiểm tra file đã ghi trước khi retry.
  7. Hoàn tất đúng phạm vi: báo file được tạo, solution được sửa, cấu hình còn cần bổ sung. Scaffold thành công chưa có nghĩa đã restore/build/deploy hay generate metadata.

Mẫu PowerShell cho guide — minh họa, chưa chạy tạo project

devkit --version
devkit new-project list --plain
devkit new-project --help

# Solution này phải tồn tại; đường dẫn chỉ là ví dụ.
$solutionPath = 'D:\work\Contoso\Contoso.slnx'
$outputRoot = 'D:\work\Contoso'
devkit new-project --type Shared --name Contoso.Shared --solution $solutionPath --out $outputRoot --plain
if ($LASTEXITCODE -ne 0) { throw 'Scaffold Shared failed; inspect output and files before retry.' }

devkit new-project --type Server --name Contoso.Server --solution $solutionPath --out $outputRoot --plain
if ($LASTEXITCODE -ne 0) { throw 'Scaffold Server failed; inspect output and files before retry.' }

Guide nên mặc định đặt --out cùng thư mục solution cho luồng chuẩn. Engine dùng WorkspaceScanner.FromSolution, handler cũng dùng workspace.SolutionDirectory; không nên hứa mọi tổ hợp solution/out khác nhau có semantics giống nhau nếu chưa kiểm tra từng handler.

Phân biệt connection: tạo Server/ConsoleCore thành công chỉ tạo project và file cấu hình/script. Bước kết nối Dataverse, sinh proxy types, deploy plugin hoặc publish webresource là hành động sau đó, dùng lệnh và quyền riêng.

07. Những điểm nên cải thiện trước MCP

Hướng dẫn lỗi cũ còn nằm trong source

TestProjectTemplateHandler còn hint devkit new --kind project ... khi thiếu Shared/ProxyTypes/SharedTest. Agent làm đúng thông báo lỗi sẽ gọi một lệnh đã bị bỏ. Đây là lỗi UX có tác động trực tiếp; sửa hint và đồng bộ docs đem lại giá trị ngay cho cả người và AI. Lần này chỉ ghi nhận, chưa sửa.

Plain text chưa phải JSON output

--plain bỏ trải nghiệm tương tác và hiển thị đơn giản; WriteResult vẫn in table/text. --json ở base args hiện chỉ file cấu hình CLI, không phải cờ xuất JSON. Nếu muốn agent/tool runner phân tích kết quả chắc chắn hơn, đề xuất thêm một option output mới, chẳng hạn --output-format json, sau khi thống nhất API.

Contract đề xuất có success, templateId, errors, warnings và files với action/path; dùng DTO chung và tách diagnostics khỏi JSON payload. Tên option/keys này là đề xuất, chưa được triển khai. Không cần thêm ngay nếu người dùng chỉ cần agent đọc text và xem diff.

Non-interactive có giới hạn về cấu hình template

TaskNewProject chỉ truyền connection từ wizard khi CanPrompt=true. Trong chế độ AI, các handler đi qua fallback/marker. Nếu người dùng muốn chọn biến thể auth hoặc options nâng cao bằng arguments, cần mở rộng contract một cách có chủ đích; thêm MCP mới cũng sẽ phải giải quyết cùng câu hỏi này.

Tạo file có thể dở dang

Engine và handlers ghi file, sinh key, sửa solution theo các bước; chưa nên coi toàn bộ thao tác là transaction có rollback. Timeout/mất kết quả không cho phép kết luận “chưa ghi gì”. Guide và adapter cần xử lý partial output, tránh retry mù hoặc dùng Force để vượt create-once.

09. Nếu làm MCP, adapter nên làm gì?

Luồng đề xuất: MCP tool → xác thực input/workspace policy → ProjectTemplateInput → ScaffoldingEngine → structured result. Gọi core trực tiếp, không gọi TaskNewProject.RunAsync vì task chứa Spectre prompt và console formatting.

  1. Tool discovery: get_templates trả kind/id/Ready/RequiresConnection cùng mô tả. Kiểm tra Ready theo handler/manifest, không chỉ trả catalog.
  2. Tool tạo project: scaffold_project yêu cầu type/name/solution/output phù hợp guide. ReadOnly=false vì ghi filesystem, dù không ghi Dataverse. Không tạo một tool riêng cho từng project type.
  3. Giữ quy tắc sản phẩm: bắt buộc solution như CLI, Force=false, không expose escape hatch chỉ vì engine có property. Engine hiện không tự bắt buộc SolutionFile khi thiếu, nên wrapper phải enforce; về lâu dài cân nhắc validator chung để tránh lệch CLI/MCP.
  4. Host không cần org cho project: hiện McpCommand kết nối ServiceClient trước RunAsync. Cần mode/profile công cụ offline hoặc host workspace riêng; không dùng ServiceClient giả. Đây là thay đổi kiến trúc đáng kể hơn thêm attribute cho một method.
  5. Workspace được cấp quyền: canonicalize output/solution; kiểm tra tên project, traversal và symlink/reparse point; không cho model chọn tùy ý mọi đường dẫn trên máy host. Cwd/roots chỉ giúp xác định vị trí, không thay thế quyền filesystem.
  6. Serialize thao tác sửa solution: lock theo solution/workspace. Registry có lock không đồng nghĩa mọi lần ghi .sln/.slnx đã được serialize. Không để hai calls đọc cùng file rồi ghi đè entry của nhau.
  7. Mutation policy: dry-run hiện mô tả và chặn Dataverse mutations. Nếu thêm file tools, phải định nghĩa rõ policy cho ghi file; không mặc định nghĩ nó đã bảo vệ scaffolding. Preview chỉ được công bố khi thật sự không ghi file/key/solution.
  8. Output và lỗi: trả DTO rõ ràng, file actions, warnings, partial failure. JSON keys của tool mới phải chốt một lần; không thay output các tool đang có.
  9. Kiểm chứng khi implementation: so sánh CLI/MCP trên cùng input; solution bắt buộc, create-once, dependency lỗi, workspace escape, concurrent calls, output và chính sách ghi file. Sau sửa MCP chạy workflow build/install/restart/whoami theo repo.

Vị trí entry tool theo quy tắc repo: namespace DynamicsCrm.DevKit.Cli.Mcp.Tools. Giữ category readonly/all theo attribute, kiểm tra các cấu trúc DisabledToolSet/ToolResourceMap/CategoryLevel; không thêm category riêng chỉ vì đây là scaffold.

Metadata chú thích tool là readonly/destructive không tự enforce quyền filesystem. Quyền thực thi cần được kiểm tra trong host/tool trước khi gọi engine. Đây là thiết kế đề xuất; hiện chưa có scaffold_project trong Mcp/Tools.
