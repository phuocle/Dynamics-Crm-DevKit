1. Kết luận nhanh (Executive Summary)

✅ KHẢ THI — và mức đầu tư hợp lý. Toàn bộ "trí tuệ" của template (nội dung payload, token, T4, metadata codegen) đã nằm ở dạng có thể chia sẻ được: payload là file vật lý trong repo, logic sinh code nằm trong DynamicsCrm.DevKit.Shared (Logic/, Services/, Resources/tt) — phần bị khóa Windows/VS chỉ là lớp vỏ: WPF forms, IWizard/EnvDTE, T4 COM service, P/Invoke sinh .snk. Chiến lược: tách phần vỏ đó bằng một Template Scaffolding Core đặt trong Shared (.shproj đã được cả VSIX net48 lẫn CLI net10 import), mỗi nền tảng chỉ còn adapter mỏng thu thập input (WPF / Spectre.Console hỏi–đáp / tham số MCP).
  • Ưu tiên 1 — CLI: lệnh mới devkit new (chế độ hỏi–đáp tương tác như CLI hiện đại + flag cho automation), chạy Windows / macOS / Linux.
  • Ưu tiên 2 — MCP: 3 tool get_templates, scaffold_project, scaffold_item gọi thẳng core — không viết lại logic.
  • VSIX giữ nguyên hành vi: từng wizard VSIX hội nhập dần về core (tùy chọn, theo từng file P/I), payload không di chuyển.

Nguyên tắc bất di bất dịch

  • Logic scaffolding tồn tại đúng 1 lần trong Shared. Adapter không chứa logic nghiệp vụ, chỉ map input/output.
  • Payload không bao giờ sao chép sang chỗ khác — 1 nguồn vật lý, các nền tảng đọc từ đó (VSIX: zip build; CLI/MCP: embedded resource).
  • Code trong Shared phải compile cho cả net48 + net10 (thói quen netstandard2.0; cấm EnvDTE/WPF/P-Invoke trong Shared).
  • Mọi thay đổi payload/token: sửa tại nguồn + cập nhật TemplateManifest + .vstemplate cùng lúc (điểm đồng bộ còn lại duy nhất, đã ghi rõ trong từng file .md).

5. Ưu điểm — Nhược điểm của phương án

✅ Pros

  • 1 nguồn sự thật: sửa template 1 lần ⇒ VSIX + CLI + MCP đồng bộ; không thể "lệch bản" giữa các nền tảng.
  • Mở khóa user Linux/macOS cho toàn bộ 30 templates bằng 1 lệnh quen thuộc devkit new.
  • Tái dùng gần như toàn bộ: T4 (.tt), resource bat/js/ts/cs, Logic codegen, MetadataService, NuGetHelper đều đã trong Shared từ trước.
  • MCP gần như free: chỉ là adapter tham số → cùng engine; AI agent scaffold project trực tiếp qua MCP.
  • CLI hỏi–đáp (Spectre.Console) cho trải nghiệm ngang wizard WPF: chọn entity/message từ metadata live.
  • Kém rủi ro cho VSIX: VSIX không phải đổi ngay; hội nhập từng wizard về core theo từng file P/I (mỗi bước đều build + test được).
  • Non-interactive flags cho CI/CD, script, và cho chính MCP dùng lại.

⚠️ Cons / Rủi ro & cách xử lý

  • Shared phải compile cả net48 + net10 — dễ vi phạm nếu dùng API .NET mới. ⇒ Giới hạn API mức netstandard2.0; build 2 phía sau mỗi thay đổi (bắt buộc trong nghiệm thu).
  • T4 output khác engine? VS COM T4 vs Mono.TextTemplating có thể lệch chi tiết. ⇒ Test chéo snapshot output 2 engine trên cùng T4Context; end-game khuyến nghị cả VSIX chuyển sang Mono impl.
  • Token semantics của VS phải mô phỏng đúng ($fileinputname$, $SafeProjectName$…). ⇒ TokenEngine port sát Replacement.cs + test từng token.
  • .shproj không add được bằng dotnet sln ⇒ SolutionMutator tự chèn entry + GlobalSection theo đúng format VS.
  • Bat là Windows-only về bản chất ⇒ các template có bat sinh thêm bản .sh tương đương trên Linux/macOS (sinh cả hai, theo OS).
  • Embed payload làm tăng size assembly (VSIX + CLI) ⇒ chỉ nhúng file thật sự cần, loại icon/bin/obj; chấp nhận tăng nhẹ.
  • Khối lượng công việc 30 templates ⇒ chính là lý do có 31 file .md chia nhỏ theo từng template, làm/check/bàn giao lần lượt.
  • Cần network cho NuGet versions ⇒ fallback offline về bộ version an toàn (đã có sẵn ý tưởng trong Replacement).

6. Lộ trình thực hiện & quy trình làm việc theo file

  • 0.md — nền móng
  • P.1 → P.13 (CLI project)
  • I.1 → I.11, I.13 → I.18 (CLI item)
  • 🤖 MCP Phase 2
  • VSIX hội nhập (tùy chọn, từng bước)

Quy trình cho AI với MỖI file .md (bắt buộc)

  1. Đọc đúng 1 file .md của template đang làm (+ 0.md nếu cần nền) — không đọc tất cả.
  2. Đọc các file nguồn được liệt kê ở mục "Nguồn sự thật hiện tại" của file đó (wizard VSIX, payload, .vstemplate, form).
  3. Implement theo mục "Việc phải làm" — handler trong Shared + đăng ký catalog + CLI wiring.
  4. Chạy build + test theo mục "Test & nghiệm thu" của file đó (dotnet build 0 err/0 warn, dotnet test, smoke CLI).
  5. Bàn giao theo checklist cuối file → user duyệt → mới được mở file kế tiếp.
Mục đích của cấu trúc này: mỗi file là một đơn vị công việc đóng hộp (scope + thiết kế + nghiệm thu), AI chỉ cần ngữ cảnh tối thiểu, giảm token đọc, có điểm kiểm soát chất lượng sau từng template.
