1 Tóm tắt điều hành & Kết luận nhanh

Anh P đặt ra 3 câu hỏi cốt lõi: (1) Gộp 42 tools xuống ít hơn có giảm mạnh token không?, (2) AI có hiểu và call dễ hơn thật không?, và (3) Tương lai anh P thêm tool #43, #44, #45... thì làm sao để không bị phình tool trở lại?

Kết luận ngắn gọn (TL;DR)
  • Giảm token RẤT LỚN — ngay mỗi lượt chat: Hiện tại 42 tools phát ra 215,375 bytes (~53.8K–61.5K tokens) mỗi lần client nạp tools/list. Gộp về 14 Domain Tools cắt xuống còn ~38.4 KB (~9.6K–11.0K tokens) — tiết kiệm ~44K–50K tokens/turn (hoặc ~24.5K–28K tokens/turn với các MCP client tự bỏ outputSchema).
  • AI hiểu và call DỄ HƠN — với điều kiện KHÔNG gộp quá mức: Vùng tối ưu (sweet spot) cho LLM function calling là 10–15 domain tools. Gộp về 14 tools giúp loại bỏ hoàn toàn sự nhầm lẫn giữa các tool chồng lấn (get_workflows vs get_flows vs get_business_process_flows vs get_business_rules; manage_ribbon vs manage_command; manage_record vs upsert_records vs manage_deleted_records), nhưng không rơi vào bẫy "God Tool" (2–4 tools) làm AI phải đoán mò tham số.
  • Triển khai 2 Phase cực an toàn, giữ 100% logic: Tất cả 42 class tool hiện tại đã tách sẵn lớp entry MCP (InvokeAsync) khỏi lớp nghiệp vụ (get_* / manage_*). Ta chỉ thêm lớp Facade Router gọi lại 42 handler cũ → 0% viết lại nghiệp vụ Dataverse, giữ nguyên DryRun fail-closed, RoleGateHelper, backup .devkit/ và toàn bộ unit tests nghiệp vụ hiện có.
  • Chống phình cho tương lai (#43, #44...): Áp dụng Ngân sách Tool (Soft Cap = 14, Hard Cap = 16) và Thang mở rộng 3 tầng: 99% tính năng mới trong tương lai (manage_dialog, manage_solution, manage_team, manage_plugin_step, manage_email_template...) chỉ thêm 1 action hoặc 1 resource vào 14 tools hiện có (~5–35 tokens) — KHÔNG thêm top-level tool mới.

4 phát hiện "ngốn token âm thầm" lớn nhất trong source code hiện tại
  1. Cú sốc outputSchema (80,180 bytes = 37.2% tổng payload!): Chỉ riêng 3 tool Read-Only get_workflows (8,528B), get_messages (7,945B) và get_business_rules (6,572B) đã ngốn 23,045 bytes vì DTO đệ quy WorkflowStepNode / WorkflowExpressionNode bị bung thành JSON Schema khổng lồ lặp lại 3 lần!
  2. Phình tham số phẳng ở các tool Schema/Command: manage_column có 39 params (8,514B inputSchema), manage_table có 30 params (5,774B — riêng cờ is_*_enabled đã 13 param), manage_command có 28 params (4,466B), manage_relationship có 23 params (2,813B).
  3. Lặp tham số env 40 lần: Chuỗi McpToolInvocation.EnvDescription (189 chars) lặp y hệt ở 40/42 tools → tốn ~9,600 bytes (~2,400 tokens) chỉ cho 1 tham số phụ!
  4. Lặp chéo WHEN TO USE & RELATED TOOLS: 42 tools chĩa link qua lại lẫn nhau tốn 41,668 bytes description; nhiều thông tin chi tiết đã có sẵn trong 14 MCP Resources (docs://, schema://) nhưng vẫn bị lặp lại trên tool schema.

5 lý do AI hiểu & gọi DỄ HƠN với 14 Domain Tools
  • Giảm áp lực phân loại (Tool Selection): Khi user hỏi "Kiểm tra xem có logic nào chạy khi update trường Credit Limit trên Account không?", trước đây AI phải cân nhắc giữa 6 tool riêng (get_plugins, get_workflows, get_business_rules, get_flows, get_business_process_flows, get_messages). Nay chỉ có 1 địa chỉ duy nhất: inspect_automation.
  • Chống "Context Rot": Cắt ~44K tokens rác khỏi đầu mỗi lượt hội thoại giúp LLM tập trung attention vào bài toán thực sự của user thay vì bị loãng bởi 441 định nghĩa tham số không liên quan.
  • Nhất quán đặt tên tham số: Toàn bộ 14 tools dùng chung 1 ngôn ngữ: resource, action, entity_name, id/name, solution_name, options/payload, env. AI học 1 lần, gọi đúng mọi tool!
  • Giữ nguyên ranh giới kinh điển của Dataverse: manage_commanding giữ nguyên luật vàng "Mặc định classic ribbon, chỉ dùng modern command khi user nói rõ Power Fx/appaction". execute_webapi giữ nguyên vai trò "cổng thoát hiểm có chặn".
  • Auto-approve tuyệt đối cho toàn bộ Phase 1: Cả 6 tool Phase 1 đều ReadOnly=true, Destructive=false, Idempotent=true → các client như Antigravity / Claude Code / Copilot / Codex cho phép chạy tự động không hỏi xác nhận.
4 rủi ro khi dùng payload JSON & Cơ chế phòng vệ 4 lớp

Khi gom 39 param của manage_column hay 30 param của manage_table vào payload (JsonObject), rủi ro duy nhất là AI gõ nhầm tên key bên trong payload. Ta triệt tiêu rủi ro này bằng 4 lớp bảo vệ bắt buộc:

  1. Lớp 1 — Hybrid Schema (Top-level Typed + Payload): 5–7 tham số dùng ở 80% lệnh gọi (resource, action, entity_name, id/name, solution_name, env) vẫn nằm trực tiếp ở top-level có kiểu rõ ràng. Các lệnh list, detail, delete, read, info hầu như không cần đụng payload.
  2. Lớp 2 — Chấp nhận song song snake_case & camelCase: Helper McpPayload đọc cả max_length lẫn maxLength, display_name lẫn displayName → triệt tiêu ~80% lỗi sai tên key thường gặp của LLM.
  3. Lớp 3 — Strict Unknown-Key Validator (Self-Healing Error): Nếu AI truyền 1 key lạ vào payload, router lập tức từ chối và trả về [Error] Unknown payload key 'foo' for manage_schema(column) kèm đúng danh sách key hợp lệ + đường dẫn docs://. AI tự sửa đúng ngay ở lượt kế tiếp, không bao giờ âm thầm bỏ qua tham số!
  4. Lớp 4 — Progressive Disclosure qua docs:// + read_instruction: Toàn bộ bảng thuộc tính chi tiết (39 field của column, 10 operations của ribbon, FormXML operations...) nằm gọn trong 10 file hướng dẫn docs://; AI chỉ nạp đúng 1 hướng dẫn khi cần ghi phức tạp thay vì trả thuế 38K token ở mọi lượt hội thoại.

4 Kiến trúc tổng thể: Facade Router + Giữ nguyên 42 Handler C#

Qua khảo sát source code, 100% các tool hiện tại đều đã tách sẵn 2 tầng: hàm InvokeAsync(...) (nhận kết nối env từ McpToolInvocation) và hàm nghiệp vụ public CallToolResult manage_xxx(...) / get_xxx(...) (được các unit test gọi trực tiếp). Nhờ vậy, ta áp dụng mẫu Zero-Rewrite Facade Pattern:

Tầng 1 · MCP Surface (14 Class có [McpServerToolType] trong DynamicsCrm.DevKit.Cli.Mcp.Tools)
Phase 1 (6 Read-Only): get_context · read_instruction · query_data · inspect_metadata · inspect_automation · inspect_diagnostics
Phase 2 (8 Mutating/Mixed): manage_data · manage_schema · manage_ui · manage_commanding · manage_logic · manage_assets · manage_admin · execute_webapi
• Tham số optional dùng nullable (string? = null) tránh bug MCP SDK 2.x #830  |  • Router đa hình dùng OutputSchemaType = typeof(JsonObject) (32 bytes!)
▼
Tầng 2 · Shared Routing Infrastructure (Mcp/Tools/Routing/McpPayload.cs + McpToolInvocation.cs)
• Resolve kết nối đa môi trường qua IMcpConnectionResolver (ConnectionBundle đã chứa đủ Client, OrgService, OrgServiceAsync, Metadata, WebApi, Options, Context)
• McpPayload: chuẩn hóa snake_case/camelCase, ép kiểu an toàn, kiểm tra ValidateAllowedKeys(...) tự động trả gợi ý sửa lỗi
▼
Tầng 3 · 42 Handler Nghiệp Vụ Hiện Có (Bỏ [McpServerToolType] / [McpServerTool], GIỮ NGUYÊN 100% CODE!)
GetTablesTool.get_tables(...), GetPluginsTool.get_plugins(...), ManageColumnTool.manage_column(...), ManageFormTool.manage_form(...), ManageRibbonTool.manage_ribbon(...), ...
• Bảo toàn nguyên vẹn: McpExecutionContext (DryRun fail-closed) · RoleGateHelper · DisplayNameFirstResolver · đường dẫn backup .devkit/manage_*/ · DTO StructuredContent · xử lý riêng cho Antigravity trong McpToolResults · toàn bộ unit test nghiệp vụ cũ!

5 Phase 1: Gộp 19 Read-Only Tools → 6 Read-Only Tools

Mục tiêu & Tác động độc lập của Phase 1 Phase 1 chỉ chạm đúng 19 tool có ReadOnly = true (không đụng 23 tool ghi/mutation). Sau khi hoàn tất Phase 1:
  • Tổng số tool toàn server giảm ngay từ 42 → 29 tools (6 RO mới + 23 RW cũ giữ nguyên).
  • Riêng khối Read-Only giảm từ 80,571 bytes → ~14,092 bytes (-82.5%, tiết kiệm ~16.6K–19.0K tokens/turn).
  • Rủi ro regression lên dữ liệu/metadata Dataverse = 0% (100% chỉ đọc). Có thể build CLI, test live kỹ lưỡng trên thực tế rồi mới bước sang Phase 2.
1. get_context — Ngữ cảnh kết nối, định danh & phân tích URL (3 → 1) ReadOnly5,252B → ~1,512B

Gộp từ: whoami (2,386B), connection_list (1,463B), parse_record_url (1,403B).

Tham số (3): action ("whoami" [mặc định] | "connections" | "parse_url"), input (URL/GUID cho parse_url), env (cho whoami / parse_url; connections chạy offline không cần xác thực Dataverse).

Điểm tinh tế: Mặc định action="whoami" giúp gọi get_context({}) vẫn kiểm tra ngay kết nối & phiên bản runtime DevKit như whoami({}) trước đây. (Xem Mục 10 nếu anh P muốn giữ riêng whoami).

// Ví dụ gọi:
get_context()                                                     // = whoami (startup env)
get_context({ action: "connections" })                            // = connection_list (offline)

2. read_instruction — Đọc tài liệu hướng dẫn docs:// & schema:// (1 → 1 · Giữ nguyên) ReadOnly2,278B → ~1,982B

Vai trò chiến lược: Là trụ cột Progressive Disclosure của toàn bộ kiến trúc mới (dành cho các MCP client không hỗ trợ resources/read). Giữ nguyên làm tool 1 tham số duy nhất (name) để AI tra cứu nhanh danh mục 14 tài nguyên mà không tốn token trong tools/list.

Sửa lỗi tiện tay: Cập nhật CatalogEntries theo tên tool mới và sửa chuỗi gợi ý lỗi ở dòng 66 từ "13 available resources (9 docs://)" thành đúng số động 14 (10 docs://, 4 schema://).

Resources liên kết: docs://data_operations_guide, docs://instructions_for_sql, schema://fetchxml.

9 Phát hiện kỹ thuật quan trọng từ MCP SDK 2.x & Ảnh hưởng toàn Repo

2 "bẫy" MCP SDK 2.x đã kiểm chứng thực tế
  1. Bẫy OutputSchemaType: Khi kiểm thử trực tiếp trên SDK đang cài trong repo, nếu đặt UseStructuredContent = true mà bỏ OutputSchemaType trên hàm trả về Task<CallToolResult>, SDK sẽ sinh ra một outputSchema sai (schema của chính CallToolResult) làm client strict bị lỗi! Cách đúng đã kiểm chứng: Đặt UseStructuredContent = true, OutputSchemaType = typeof(JsonObject) → SDK phát đúng "outputSchema":{"type":"object"} (chỉ 32 bytes!) và tương thích 100% mọi DTO trả về.
  2. Bẫy string param = "" (issue csharp-sdk#830): MCP SDK 2.x coi tham số string non-nullable có default "" là required trong JSON Schema! Mọi tham số tùy chọn trên 14 router mới bắt buộc khai báo nullable: string? = null, int? = null, bool? = null, JsonObject? = null.
